# Octopus Embedded

> 面向工业网关、高可靠联网设备与 AI 边缘具身机器人的**跨 SoC 高可靠嵌入式 Linux** 软件平台。

**Octopus Embedded**（Octopus 嵌入式平台）是一套开源嵌入式底座，面向需要 **7×24 长期稳定运行** 的现场设备场景。首批以瑞芯微 RK3568、星宸 SSD20X、全志等 SoC 为适配目标，整体架构可扩展至市场上大多数同档位的 ARM 嵌入式应用处理器（工业网关与边缘计算场景）。平台提供统一的固件防变砖、进程监护、一体化管理面、存储抽象与模块化业务扩展能力。

> **当前阶段：** 架构设计规范与核心 RFC 论证已公开，欢迎参与开源讨论。**源代码编码将于阶段 1 正式启动** —— 进度见 [ROADMAP.md](ROADMAP.md)。

## 名词说明

下面四组词在本文中反复出现。它们描述的是同一套做法：设备里如何存放系统，以及每次上电、每次升级之后启动哪一份。先看示意图，再看定义。

### 图 1：Flash 物理布局

```text
  +---------------+  +---------------------+ +---------------------+
  |  1. BOOT      |  |  4. SLOT_A          | |  5. SLOT_B          |
  |  SPL + U-Boot |  |  firmware slot A    | |  firmware slot B    |
  +---------------+  +---------------------+ +---------------------+
                     |  kernel + rootfs    | |  kernel + rootfs    |
                     +---------------------+ +---------------------+

  +---------------+  +---------------------------------+
  |  2. ENV       |  |  6. DATA                        |
  |  boot_slot    |  |  user config + logs             |
  |  slot states  |  +---------------------------------+
  |  bootcount    |  +-----------------+
  +---------------+  |  3. FACTORY     |
                     |  MAC / SN       |
                     +-----------------+
```

**图中各块的说明**

| 块 | 作用 | 升级是否涉及 |
|:---|:---|:---|
| `1. BOOT` | 引导程序（SPL + U-Boot）。产线烧录一次 | 不涉及 |
| `2. ENV` | 启动参数区（双副本互备）。记录本次从哪个槽启动、各槽状态、连续启动失败次数 | 升级过程会读写 |
| `3. FACTORY` | 出厂信息：MAC 地址、序列号、产线校准参数。物理写保护 | 不涉及 |
| `4. SLOT_A` / `5. SLOT_B` | **固件槽位**：各放一整份可启动的系统（内核 + 根文件系统），格式统一为 OFI | 升级写入未运行的那个槽 |
| `6. DATA` | 用户配置与日志（含审计与诊断）。**不属于任何槽位** | 升级不覆盖；出厂重置只清这一块 |

> **看图提示**：`4`、`5` 两块是**同一种格式的两份完整系统**（A/B 双槽）；左列 `1`、`2`、`3` 属于引导链，产线固化后远程升级不涉及；`6` 是用户数据区，与固件版本无关。
>
> **排版说明**：框内只使用 ASCII 字符（`+ - |`），中文说明一律放在框外，因此**框线与字体无关、必然对齐**。

### 图 2：双槽 OTA 与回退

```text
  normal operation
  +--------------------------+   +--------------------------+
  |  SLOT_A                  |   |  SLOT_B                  |
  |  system image 1          |   |  system image 2          |
  |  [ RUNNING ]             |   |  [ STANDBY ]             |
  +--------------------------+   +--------------------------+
               |
               |  OTA: write new image into the slot that is NOT running
               |  the running slot stays untouched, so rollback stays possible
               v
  first boot after OTA
  +--------------------------+   +--------------------------+
  |  SLOT_A                  |   |  SLOT_B                  |
  |  old version             |   |  new version             |
  |  [ still bootable ]      |   |  [ TRYING ]              |
  +--------------------------+   +--------------------------+
               |                              |
        boot ok / self-check ok          boot fail / self-check fail
               |                              |
               v                              v
     confirm slot B: mark VALID        bootloader follows ENV, boots A again
     next boot uses slot B             -> version rollback, device stays bootable
```

> 中文对应：`RUNNING` = 正在运行；`STANDBY` = 备用；`TRYING` = 试运行（尚未确认）；`still bootable` = 仍可启动，用于回退；写进 `ENV` 的就是"下次从哪个槽启动"。

### 名词定义

| 名词 | 含义 |
|:---|:---|
| **固件槽位** | 图 1 中的 `SLOT_A` 或 `SLOT_B`。Flash 上划出的一块区域，里面放**一整份可以启动的系统**（内核 + 根文件系统）。上电后引导程序从其中一个槽位把系统读进内存并启动。 |
| **双槽** | 图 1 中 `SLOT_A` 与 `SLOT_B` 这两块同时存在的做法（图 2 的流程）。两个对等的固件槽位，设备平时只运行其中一个。远程升级把新固件写进当前没有运行的那个槽；确认新固件能正常启动后，下次开机改为从新槽启动；新固件若连续启动失败，引导程序改回仍然完好的旧槽。 |
| **A/B 仲裁** | 图 2 中"选哪个槽启动"的那段判断逻辑，具体依据是图 1 中 `ENV` 里记录的**槽位状态**（可用 / 试运行 / 已损坏）与**连续启动失败次数**。芯片原厂 SDK 通常把这段判断写成该芯片专用的启动脚本，下表中的「A/B 仲裁脚本」就是指它。Octopus 把同一套判断写成统一的「双槽状态机」，换芯片时这套规则保持不变。 |
| **OFI 镜像格式** | 图 1 中写进 `SLOT_A` / `SLOT_B` 的固件包的统一格式，全称 Octopus Firmware Image，扩展名 `.ofi`。它规定了头部、签名与内核 / 根文件系统 / AI 模型各段如何排列，因此换芯片时打包方式不变。 |

### 两个容易混的地方

1. **这里的"槽"只指系统固件，不是用户数据区。** 用户配置和日志在图 1 的 `6. DATA` 那一块，不属于任何槽位，升级或切换版本都不会覆盖它。（注意：只读根文件系统合成的机型上，需要长期保存的运行期文件必须显式放到 `/data`，放到 `/etc` 之类的路径重启即丢。）
2. **双槽 ≠ 双系统同时在跑。** 任何时刻只有一个槽在运行，另一个只是"随时可以启动"的备份。因此升级当前没在运行的那个槽，不会影响正在工作的系统，升级失败也能启动回旧版本。

## 为什么需要 Octopus Embedded？

在嵌入式 Linux 产品开发与工业量产实践中，研发团队普遍面临 8 大真实工程困境：

| 真实工程痛点 | 工业现场与研发后果 | Octopus Embedded 破局之道 |
|:---|:---|:---|
| **芯片 SDK 强绑定** | 每次因降本或缺货换一款 SoC（如 RK3568 换 SSD20X），烧录工装、打包格式、以及上电时选择启动哪个槽位的 A/B 仲裁脚本全部重写 | **统一平台外壳**：固化全生命周期规范（OFI 镜像格式、双槽状态机：两份固件如何切换、失败如何回退）；芯片差异收敛于设备树与极薄 Board HAL |
| **存储介质更替重构** | 单板降本换料（NOR / SPI-NAND / eMMC），物理坏块跳过、MTD 字符设备与块设备差异导致 OTA 写入与启动逻辑崩溃 | **存储抽象层（SAL）**：全系统统一抽象 6 大逻辑卷，SPI-NAND 上存放系统固件的槽位交由 UBI 管理坏块，数据区自适应文件系统（JFFS2/UBIFS/ext4） |
| **管理面多入口各写各的** | CLI、Web、云端 RPC、本机 HDMI/LCD 界面各自写一套解析器，串口改过屏上看不到，屏上保存又盖掉云端；断电写配置导致文件截断损坏 | **单一真相与配置事务**：本地屏、Web、CLI、RPC、云端全部读写同一份 Candidate-Running 配置（候选配置与运行配置），带冲突检测与确认式提交；纯文本分层配置宽容重放，POSIX 安全存盘管道 |
| **PID 1 进程编排两极困境** | `systemd` 连同配套组件常驻数十 MB 量级，小内存网关需大量裁剪；`BusyBox init` 虽能 respawn，但没有依赖顺序、就绪通知与退避 | **轻量级 PID 1 监护**：<2000 行纯 C 实现的 `octopus_supervisor`，支持声明式 DAG 依赖启动、阶梯退避重启与优雅关机（<2 MB RAM） |
| **现场偶发死机排查黑盒化** | 现场偶发死锁或崩溃，硬件看门狗复位后现场日志一片空白；小内存 Flash 无法存 Core Dump，研发陷入「无法复现」的售后死循环 | **系统自省与死机黑匣子**：内置 `lock_watchdog` 互斥锁监护；堆内存按模块统计分配与释放，用来看出是哪个模块在漏内存；调试固件另在每块内存前后写下固定校验值（俗称金丝雀值），释放时若校验值被改写，即可判定发生了越界踩踏；崩溃时抓取全线程调用栈，写入 RAMoops/Flash 黑匣子 |
| **突发掉电根文件系统损坏** | 工厂或野外随时拉闸断电，读写混合分区元数据受损导致开机 Kernel Panic 无法挂载根分区，现场只能返厂 | **只读底座动态合成**：基于 initramfs 的 `octopus_loader`，将只读 SquashFS 与内存 tmpfs 合成为可写的 OverlayFS 根目录（重启即还原），持久数据严格隔离 |
| **AI 边缘「大小脑」通信瓶颈** | 运动控制与厂商 NPU 用户态运行时塞在同一进程（NPU 侧故障拖垮整机）；用本地 Socket 传输高清视频流拷贝开销巨大，CPU 打满 | **双平面物理隔离**：控制面走轻量 JSON-RPC（故障域隔离）；高吞吐图像/张量数据面走 POSIX 共享内存零拷贝环形队列 |
| **通用升级框架落地断层** | SWUpdate、RAUC 等开源框架只管把镜像写进分区，假定 U-Boot 已具备选槽与坏块处理，也不管配置版本迁移与进程生命周期，在 64 MB RAM 的紧凑网关上难以裁剪 | **自研全链路而非套壳**：选槽与坏块语义在 U-Boot 与用户态两侧对称实现，升级、配置迁移、进程编排、死机自愈由同一套底座协同 |

### 这 8 个困境在团队日常中的样子

下面 8 条覆盖上表这 8 类困境，只是换成研发团队在一个典型产品周期里实际经历的版本。如果你做过嵌入式量产，大概会对其中几条有画面。

1. **「换一颗 SoC，脱一层皮」**：芯片厂商提供的 SDK 往往不只交付内核驱动，还硬塞了一套封闭的「固件全生命周期机制」（芯片专用镜像打包器、配套烧录工具、写死的分区表与升级脚本）。每次单板芯片换型，研发团队 70% 的精力都耗费在重写产线烧录脚本和升级回退状态机上。
2. **「Flash 换料引发的 OTA 灾难」**：为了降本把单板从 eMMC 改为 SPI-NAND，开发人员很快发现裸 Flash 存在出厂坏块和运行时新坏块，普通 `dd` 刷写直接报废；U-Boot 读取拓扑与用户态写入拓扑不一致，导致固件无法引导。
3. **「CLI、Web、RPC、本地屏各写各的」**：同一个设备参数，串口改过 Web 上看不到，本机 HDMI/LCD 界面又维护一份自己的配置；屏上一点保存，把云端和命令行刚改的值盖掉。写配置文件途中断电，文件变成空文件，下次启动业务起不来。
4. **「小网关跑不动 systemd，BusyBox 又管不住崩溃」**：在 64 MB ~ 128 MB 的小内存网关上，完整的 `systemd` 组件栈占掉相当比例的内存，要启动快必须大量裁剪；退回 BusyBox 则没有依赖顺序和健康检查，服务反复崩溃时要么被无限快速重拉，要么停在「进程还在、服务已死」的假死状态。
5. **「客户现场死机，售后回传『现场已重启，查无原因』」**：设备在野外连续运行 3 个月后偶发死机，看门狗复位后现场干干净净。嵌入式 Flash 容量极小，无法落盘几十兆的 Core Dump，慢速微量内存泄漏与 ABBA 互斥锁死锁难以溯源。
6. **「现场暴力拉闸断电即变砖」**：工业现场工人频繁拔电，若根文件系统是读写混合的 ext4 或 ubifs，元数据损坏即无法开机，维护成本极其高昂。
7. **「NPU 一崩，整机陪葬」**：运动控制这一路要求毫秒级确定性，视觉推理那一路依赖厂商交付的 NPU 用户态运行时；两者塞进同一个进程，NPU 侧出问题就把整机拖死，而把高清视频流改走本地 Socket 又要付出大量内存拷贝，CPU 直接打满。
8. **「升级框架套上去，坑还得自己填」**：SWUpdate、RAUC 这类开源框架能解决用户态写入与双槽切换的通用部分，但它们假定 Bootloader 已经会选槽、会跳坏块，也不管配置版本怎么迁移、进程崩了谁来拉、死机了怎么自愈。团队把框架接进来，才发现真正难的一段仍要自己写，而且在 64 MB RAM 的紧凑网关上还得先把它裁到跑得动。

## 适用场景

- **工业与高可靠网关** — 路由、双槽固件 OTA（升级失败可回退到槽 A）、现场诊断
- **带本地屏的设备** — HDMI / LCD 界面与 Web、CLI、云端共用同一份配置
- **AI 边缘与具身机器人** — 小脑主进程 + 可选 NPU 视觉独立进程
- **跨芯片产品线** — 同一套代码，不同工具链（RK3568 / SSD20X / …）
