# Octopus 通用底座技术栈与编程语言选型规范

**简体中文** | [English](./00-language-cpp-guidelines.en.md)

> **文档定位**：针对嵌入式开发者与系统架构师关心的核心问题——“整个 Octopus 架构是否应全部用纯 C 语言重写？”，从**系统安全性、开发效率、内存管理、跨语言生态与长期维护性**等维度进行深度技术论证，明确划定各系统层级的语言边界，并确立**工业级嵌入式 C++ 的克制使用准则**。

---

## 1. 核心结论：为什么不应全部使用纯 C 语言？

**明确结论：Octopus 底座绝不建议全部用纯 C 编写。**

在嵌入式 Linux 系统级软件设计中，“纯 C 原教旨主义”看似贴近底层，但在面对“高可靠管理面、动态配置反射、多线程并发安全”时，会迅速演变为维护灾难。

工业级软件的黄金法则应当是：  
**“离硬件越近越纯 C，底座核心用轻量 C++，对外边界一律纯 C，上层业务自由多语言。”**

---

## 2. 深入剖析：若核心底座退回纯 C 会遭遇的两大灾难

经典工业级商用网络操作系统之所以能长期稳定支撑复杂管理面，其最核心的技术壁垒之一就是用户态主程序中高度成熟的 **C++ 模板元编程与反射体系**。如果强行用纯 C 重写核心底座，将面临两大不可承受之痛：

### 2.1 痛点一：丢掉“编译期模板反射”，管理面沦为代码地狱

在 Octopus 架构中，系统对外提供统一的管理面（octopus_cli 命令行、Web 网页、JSON-RPC / IPC、octopus_config 纯文本配置存盘恢复）。

#### 在轻量 C++ 下（现状）：
开发者只需定义一个纯业务 C 结构体，然后写**一行模板注册代码**：
```cpp
// 仅此一行，C++ 模板利用编译期推导，自动完成：
// 1. JSON-RPC 方法树挂载与参数自动校验；
// 2. Web 前端请求自动反序列化；
// 3. Unix Domain Socket 本地 IPC 接口暴露；
// 4. octopus_config running-config 文本序列化存盘与开机逐行重放解析。
StructReadWrite<my_device_cfg_t>(&ns_system, "config", get_cfg, set_cfg);
```
- **机制**：由编译器在编译期自动生成针对每个数据类型的读写特化代码，**运行期零开销，类型绝对安全**。

#### 若强行退回纯 C：
C 语言缺乏泛型、模板与运算符重载机制。为了实现相同的全套功能，开发者必须：
1. **手工硬编码 cJSON 解析**：为成百上千个结构体的每一个字段逐行编写 `cJSON_GetObjectItem`、类型判断、边界检查与错误处理代码；
2. **手写序列化与反序列化**：每个配置项都要写一套存盘字符串格式化与逐行正则匹配重放代码；
3. **或陷入“宏地狱（X-Macros / 嵌套宏）”**：用满屏的 `##`、`#` 宏拼装复杂的函数定义，使得编译报错信息完全不可读，IDE 无法进行符号跳转与语法高亮，Bug 极难排查。

> **代价评估**：用纯 C 实现同样的一体化管理面，**代码量将暴增 3~5 倍**，且每一次字段增删改都需要在五六处地方手工同步修改，极易发生打字错误与类型不匹配导致的段错误。

---

### 2.2 痛点二：高并发下的锁与资源泄漏（缺乏 RAII 机制）

`octopus_app` 是一个长期常驻的多线程主进程（Reactor 主循环、2~4 个 Worker 线程、看门狗巡检线程，以及路由事件监听、硬件状态轮询等模块线程），涉及海量的互斥锁（Mutex）、文件描述符（FD）和临时动态缓冲。

#### 在轻量 C++ 下（现状）：
充分利用 **RAII（Resource Acquisition Is Initialization，资源获取即初始化）** 机制：
```cpp
void handle_port_event(int port_no) {
    // 进入作用域自动上锁；无论后续从何处 return、break，离开作用域必然自动解锁！
    std::lock_guard<std::mutex> lock(g_port_mutex);

    if (!is_valid(port_no)) {
        return; // 安全退出，锁自动释放
    }
    // 业务逻辑...
}
```

#### 若强行退回纯 C：
C 语言没有析构函数（Destructor），开发者必须依赖严格的人肉排查与 `goto` 级联跳转：
```c
int handle_port_event(int port_no) {
    pthread_mutex_lock(&g_port_mutex);

    if (!is_valid(port_no)) {
        pthread_mutex_unlock(&g_port_mutex); // 极易遗忘解锁！
        return -1;
    }

    int fd = open("/dev/xxx", O_RDWR);
    if (fd < 0) {
        goto out_unlock; // 一旦跳错标签，就会引发死锁或句柄泄漏
    }

    // 更多分支...
out_unlock:
    pthread_mutex_unlock(&g_port_mutex);
    return ret;
}
```
在需要长期连续无故障运行数月乃至数年的工业与车载设备中，**纯 C 多分支逻辑下遗漏一次解锁就会导致死锁，整机卡死变砖；遗漏一次 `close(fd)` 就会耗尽句柄**。

## 3. Octopus 全局技术栈与语言选型矩阵

遵循**“内聚用 C++，边界与底层用纯 C”**的原则，Octopus 各系统层级划分出清晰的语言职责边界：

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 4. 应用与扩展层:                                                        │
 │    - Web 前端: HTML5 + 现代 JavaScript (Vue / 原生轻量 JS)              │
 │    - 独立 AI 视觉进程 (ai_vision_daemon): C++ (C++14/17, 可选链厂商 NPU/RGA 库)│
 │    - 客户独立业务进程: 任意语言 (Python / Go / Rust / 纯 C)             │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 3. 核心底座主进程 (octopus_app):                                       │
 │    - 业务模块池 (In-Tree Modules): 轻量 C++ (C++11/14)                 │
 │    - 管理面引擎 (octopus_cli / JSON-RPC / octopus_config): 轻量 C++ (C++11/14)          │
 │    - 核心公共库 (liboctopus_basics): 轻量 C++ (OSAL / 反射 / 日志)      │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 2. 对外二次开发 SDK 与中间件接口 (Boundary Layer):                      │
 │    - liboctopus_client SDK: 纯 C (C99, 零第三方依赖, extern "C")       │
 │    - 服务监护 (octopus_supervisor / octopus_loader): 纯 C (C99)        │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 1. 硬件驱动、引导与操作系统层 (OS & Hardware Layer):                    │
 │    - 板级 Board HAL (liboctopus_board): 纯 C (C99)                     │
 │    - 交换芯片驱动 (交换芯片 SDK / 板级交换适配层): 纯 C (C99)                            │
 │    - Bootloader 与 Linux 内核 (U-Boot / cmd_ofi.c / Kernel): 纯 C (C99)│
 └────────────────────────────────────────────────────────────────────────┘
```

### 详细选型依据对照表

| 层级 / 模块划分 | 语言选型 | 核心考量与技术依据 |
| :--- | :--- | :--- |
| **Bootloader 与引导** (`cmd_ofi.c` / U-Boot 补丁) | **纯 C (C99)** | U-Boot 裸机环境与内存受限阶段，必须使用绝对标准 C 语言。 |
| **Linux 内核与设备驱动** (内核模块、DTS 设备树) | **纯 C (C89/C99)** | Linux 内核官方标准语言，直接操作硬件物理寄存器。 |
| **板级 Board HAL** (`liboctopus_board`) | **纯 C (C99)** | 声明极简 C 头文件，负责读取 MAC、SN、操作 LED 与出厂按键，为所有应用提供最稳定的 C ABI。 |
| **芯片硬件直通库** (交换芯片 SDK / 板级交换适配层) | **纯 C (C99)** | 交换芯片厂商提供的用户态 C 库，通过 UIO 与内核 `mmap` 进行物理寄存器交互。 |
| **对外二次开发 SDK** (`liboctopus_client`) | **纯 C (C99)** | **至关重要的架构边界**：对外交付的头文件和动态库全为纯 C 实现（零 C++ 依赖、零 STL 依赖），保证 Python/Go/Rust/纯 C 的外部进程均可无缝直接绑定。 |
| **核心支撑库** (`liboctopus_basics`) | **轻量 C++ (C++11/14)** | 提供 OSAL 线程锁封装、`StructReadWrite` 模板反射、分级 Trace 日志系统。 |
| **核心管理面中间件** (octopus_cli / JSON / octopus_config) | **轻量 C++ (C++11/14)** | 承载全局 `JSON_RPC_ROOT` 方法树路由、纯文本配置序列化与重放逻辑。 |
| **核心主进程入口与模块** (`octopus_app`) | **轻量 C++ (C++11/14)** | `main.cxx` 生命周期广播与业务组件调度，兼顾高性能与代码复用。 |
| **Initramfs 根文件系统引导** (`octopus_loader`) | **纯 C (C99)** | initramfs 阶段 PID 1，挂载 OverlayFS 叠加 SquashFS 层，`switch_root` 后 exec 至 `octopus_supervisor`（initramfs 不能用 `pivot_root`）。静态链接，不依赖 C++ 运行时。 |
| **PID 1 进程监护器** (`octopus_supervisor`) | **纯 C (C99)** | 与架构文档 5.2 一致：< 2000 行纯 C，单线程，启动后不再动态分配内存。PID 1 一旦崩溃内核即 panic，因此不引入 C++ 运行时和 STL。 |
| **独立 AI 视觉守护** (`ai_vision_daemon`) | **C++ (C++14/17)** | 可选链接 OpenCV、板级 RGA 以及芯片厂商按许可另行提供的 NPU 用户态 SDK（不纳入本仓库）；此类 SDK 多为 C++ 接口，故该进程选用 C++。 |
| **Web 前端管理界面** | **HTML5 + 原生 JS / Vue** | 运行于客户端浏览器，通过 HTTP POST 提交 JSON-RPC，后端无任何 PHP/Python 动态环境。 |
| **Host 构建工具** (`ocli_tool`, `ofi_pack`) | **C++ / Python / Shell** | 在编译机（PC/服务器）运行，用于离线语法编译与 OFI 镜像打包。 |

## 4. 嵌入式 C++ 的克制使用准则

在工业与嵌入式领域使用 C++，**绝不能像在 x86 服务器端那样任意挥霍现代 C++ 特性**，而是必须将其作为**“具备强类型安全、编译期模板与 RAII 的工业级 C”**（C with Classes and Templates）来对待。

在 `octopus-core` 编译与编码中，必须严格恪守以下**五项准则**。

**语言标准基线**：`octopus-core` 以 **C++14** 为基线。C++17 特性（`std::optional`、`if constexpr` 等）只有在所有目标 SoC 的交叉工具链都确认为 GCC ≥ 8 后才允许使用，并在顶层 CMake 中统一切换，不允许个别模块单独提升标准。

**适用范围**：以下准则约束 `octopus-core`（`octopus_app` 与 `liboctopus_*`）。`ai_vision_daemon` 等独立进程若链接 OpenCV 或厂商 NPU 用户态库等依赖异常与 RTTI 的第三方 C++ 组件，可以不开启 `-fno-exceptions` / `-fno-rtti`，但不得把这些库链接进 `octopus_app`；厂商库须按厂商许可由设备方自行获取，**不得提交进本仓库**。

### 准则 1：强制关闭 RTTI 与重度异常机制
- **CMake 编译选项强制约束**：
  ```cmake
  add_compile_options(-fno-rtti -fno-exceptions)
  ```
- **技术依据**：
  - **RTTI（运行时类型识别）** 会为每个类生成 `type_info` 数据结构，增大只读数据段体积并产生动态开销；
  - **异常（Exceptions）** 会引入庞大的异常处理表（`.eh_frame`），破坏确定性的实时响应时间，并增加堆栈展开的不确定风险。
- **错误处理规范**：
  所有模块内部统一使用强类型状态码枚举（如 `octopus_rc_t`）或结果体（C++17 启用后可用 `std::optional`）传递错误，禁止抛出异常。
- **注意 `-fno-exceptions` 下的内存分配失败**：STL 容器与 `new` 分配失败时无法抛出 `std::bad_alloc`，进程会直接 abort。这与 Octopus 的故障模型一致（崩溃转储 → supervisor 重启），但意味着“内存不足”不是可恢复错误。可预见的大块分配（如接收固件分片、大配置导入）应使用 `new (std::nothrow)` 或预分配缓冲并显式检查。

### 准则 2：严禁引入庞大臃肿的外部第三方 C++ 库
- **严禁依赖 Boost 等重型框架**：嵌入式设备的 Flash/RAM 资源极其宝贵，引入重型库会导致二进制暴增数十兆，依赖关系复杂混乱；
- **底座自力更生**：基础线程、锁、消息队列由 Octopus 自研的 `liboctopus_basics`（OSAL）直接对接 Linux POSIX 接口实现；轻量容器仅使用基础 STL（如 `std::vector`、`std::string`、`std::map`）。

### 准则 3：严格控制动态堆内存分配（杜绝内存碎片化）
- **数据面零动态内存分配**：在关键实时数据收发路径（如网络报文收发、电机角度控制循环、传感器采样定时器）中，**严禁在运行时循环调用 `new` / `malloc`**；
- **优先采用预分配机制**：采用静态数组、固定大小环形缓冲区（Ring Buffer）或固定块内存池（Memory Pool），消除长期运行产生的堆内存碎片。

### 准则 4：扁平结构优先，严禁复杂的多重继承树
- 避免使用深层类继承与复杂虚基类（Virtual Base Classes），虚函数表（vtable）的层级过深会增加函数指针跳转间接寻址开销，破坏 CPU 指令缓存（I-Cache）局部性；
- 优先采用**对象组合（Composition）**与**结构体映射（POD 结构体）**。

### 准则 5：规范 RAII 的使用边界
- 所有的互斥锁必须使用 `std::lock_guard` 或 `std::unique_lock` 封装，杜绝任何手动 `pthread_mutex_unlock`；
- 所有动态申请的临时文件描述符（FD）和 Socket，必须封装在生命周期看护类中，确保离开作用域时必然被 `close()`。

## 5. 架构的黄金分界：“内聚用 C++，边界用纯 C”

Octopus 架构最优雅的地方在于其边界处理机制——**内部的高效与外部的兼容完美并存**：

```text
  ┌────────────────────────────────────────────────────────┐
  │                 【octopus-core 内部】                  │
  │  - 使用现代轻量 C++ (C++11/14)                         │
  │  - 享受 StructReadWrite 模板自动反射带来的代码极简化    │
  │  - 享受 RAII 带来的锁安全与零泄漏                      │
  │  - 模块间在内存中指针直调，效率达到极致               │
  └───────────────────────────┬────────────────────────────┘
                              │
                              │ 跨出进程边界或板级边界
                              ▼
  ══════════════════════════════════════════════════════════
               【黄金分界面：严格 extern "C"】
      (头文件与动态库：liboctopus_client.h, board_hal.h)
  ══════════════════════════════════════════════════════════
                              │
                              │ 纯 C ABI，无任何 C++ 符号混淆 (Name Mangling)
                              ▼
  ┌────────────────────────────────────────────────────────┐
  │                 【外部生态与客户业务】                 │
  │  - 客户用 Python 直接调用 ctypes / cffi 接入底座       │
  │  - 客户用 Go / Rust / 纯 C 编写独立进程直连 IPC Socket │
  │  - 板级硬件驱动无需关心用户态逻辑，只对齐纯 C 接口     │
  └────────────────────────────────────────────────────────┘
```

1. **对内（In-Tree）**：
   内部开发人员通过 C++ 模板获得十倍的开发与维护效率，只需定义结构体即可自动拥有 Web/CLI/octopus_config 全套管理面，代码量减少 70% 以上；
2. **对外（Out-of-Tree & HAL）**：
   暴露给客户的 SDK（`liboctopus_client`）和板级接口（`liboctopus_board`）都是**最纯粹的 C99 接口**。外部开发者不需要安装任何 C++ 运行时，不受 C++ 编译器版本和标准库 ABI 变动的困扰，用任何现代语言均可在数分钟内完成与 Octopus 底座的对接。

## 6. 总结

| 考量维度 | 纯 C 方案 | Octopus 选定的“轻量 C++ 核心 + 纯 C 边界”方案 |
| :--- | :--- | :--- |
| **代码量与维护成本** | 极高（需手写数万行 cJSON 解析与序列化样板代码） | **极低（一行 C++ 模板自动生成 Web/CLI/octopus_config 闭环）** |
| **长期高并发安全性** | 脆弱（依赖人肉检查 goto 解锁，易漏解死锁） | **极高（通过 RAII 自动析构加解锁，从语法层面杜绝死锁）** |
| **固件与内存占用** | 极小 | **极小（禁用 RTTI 与异常，与纯 C 相比体积增加 < 5%）** |
| **跨语言二次开发生态** | 良好 | **完美（对外边界全为纯 C 头文件，跨语言调用零阻碍）** |
| **现代 AI / 视觉集成** | 困难（主流算法 / 板级加速 SDK 几乎全为 C++ 封装） | **可行（独立进程可对接 OpenCV、RGA 及厂商 NPU 用户态 SDK 的 C++ 接口）** |

因此，**“保留轻量 C++ 用于底座核心与模板反射，使用纯 C 固化底层驱动与对外 SDK”**，是兼顾了极致性能、高可靠性、开发效率与开放生态的唯一最佳选择。
