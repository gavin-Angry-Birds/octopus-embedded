## 1. 场景定位与可行性论证：这套架构能做机器人吗？

**核心结论（在底座 Phase 3 Blockers 收敛且按规范落地的前提下）：** 可以做。相对实验室里用原生桌面 Linux 或 Python 脚本拼装的方案，Octopus 在远程 OTA 回退、掉电下根文件系统保护、进程故障域隔离与配置原子落盘上有明确架构抓手；但这**不是**「已经量产验证、全面碾压」的承诺，实时运动控制与功能安全仍须单独设计（见第 13 章）。

### 1.1 机器人与智能硬件的商用核心命门
很多开发者用标准 Ubuntu/Debian 跑 ROS 或 Python 写机器人，在实验室演示很完美，但一旦推向商用量产就会暴露出致命痛点：
1. **远程 OTA 变砖风险极高**：机器人跑在用户家中或野外，断电或断网导致升级中断，设备直接变砖无法开机；
2. **强行拔电/耗尽电量损坏文件系统**：机器人常因电量耗尽或直接关断总电源而掉电，传统可读写 EXT4 文件系统极易损坏；
3. **AI 进程崩溃拉着整机瘫痪**：NPU 模型推理、摄像头视频流非常容易偶发内存越界或死锁，导致整个系统假死；
4. **校准参数容易丢失或混乱**：机械臂零偏、舵机校准角度、PID 控制参数、Wi-Fi 凭证缺乏可靠的原子持久化管理。

### 1.2 Octopus 架构降维打击的四大优势
- **OFI 固件 + A/B 双分区 + 启动计数器**：实现真正的“防变砖 OTA”，新固件异常自动回退到旧系统；
- **只读 SquashFS + 内存 OverlayFS**：哪怕机器人强拔电池 1000 次，底层文件系统永远处于只读保护状态，开机完好如初；
- **PID 1 octopus_supervisor 的崩溃秒级自愈**：上层视觉或 AI 算法偶发段错误，底座小脑依然平稳控机，octopus_supervisor 在 1 秒内重启 AI 进程；
- **octopus_config 文本式参数存盘引擎**：舵机偏移量、用户配置、网络参数提交即生效，后台合并后原子落盘（通常在数秒内完成），开机自动重放恢复；掉电最多丢失最后几秒内尚未落盘的修改，已落盘的配置不会损坏。

## 2. 核心架构模式：动静分离与两栖分工

在机器人系统中，必须严格贯彻**“小脑（稳态底座）与大脑（AI 视觉）动静分离”**的原则：

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 传统脆弱架构 (反面教材):                                               │
 │  把摄像头取流、OpenCV、NPU 模型、电机驱动、Web 交互全塞在单一进程里   │
 │  ==> NPU 偶尔内存泄漏或模型推理超时 -> 整个进程崩溃 -> 机器人直接翻倒死机│
 └────────────────────────────────────────────────────────────────────────┘
                                    VS
 ┌────────────────────────────────────────────────────────────────────────┐
 │ Octopus 稳健机器人架构 (优雅模式):                                     │
 │  - 大脑 (AI/NPU 独立进程): 专注高负载模型推理，死掉由 octopus_supervisor 秒级重启 │
 │  - 小脑 (Octopus 主底座): 专注底盘电机、电源管理、安全看门狗、OTA 升级 │
 └────────────────────────────────────────────────────────────────────────┘
```

1. **Octopus 核心主进程 (`/usr/bin/octopus_app`) —— 充当“管家”**：
   - 负责系统网络管理、OTA 升级仲裁、用户参数保存（octopus_config）、电池电量监测与告警；
   - 向运动控制下发目标（姿态、速度、动作序列），不亲自跑闭环；
2. **运动控制（`motion_ctrl` 实时进程或外挂 MCU）—— 真正的“小脑”**：
   - 负责电机 PWM、舵机逆运动学解算、跌落防撞保护这类毫秒级闭环；
   - 不能放在 `octopus_app` 里：`octopus_app` 的主循环要处理 RPC、配置事务、日志，架构文档 3.2 明确禁止其中出现重度耗时操作，它的调度延迟也无法保证 1ms 级闭环。放在同一进程还意味着配置模块的一次崩溃就会让电机失控；
   - Linux 侧实现需 `SCHED_FIFO` + `mlockall()` + CPU 隔离，闭环周期 ≤ 1ms 时建议 PREEMPT_RT 内核或直接交给 MCU；
   - **安全状态**：控制进程停止刷新目标超过设定时间（如 50ms），电机驱动器或 MCU 必须自行进入安全状态（停转、断扭矩或保持），不能依赖 Linux 侧“重启后再恢复”；
3. **外部独立 AI 守护进程 (`/usr/bin/ai_vision_daemon`) —— 充当“眼睛与大脑”**：
   - 独立进程运行，独占 NPU 芯片和摄像头驱动；
   - 负责视频采集、目标识别（人/动物）、模型推理；
   - 通过极轻量的本地 Unix 套接字 `/var/run/json_ipc.socket` 与主底座小脑通信。

## 3. 典型需求落地：摄像头识别动物/人物并传送云端

这是一个标准的 **“边缘感知（Edge AI）+ 本地物理联动 + 物联网上云（IoT）”** 闭环。

### 3.1 全链路端到端数据流

```text
 [ 1. 物理采集 ] 摄像头 (MIPI-CSI / USB) 捕获原始视频流 (NV12/YUV)
        │
        ▼ 硬件零拷贝 (DMA-BUF / RGA 图像硬件裁剪缩放)
 [ 2. 边缘推理 ] RK3568 NPU 运行轻量模型 (如 YOLOv8n-nano)
        │       输出识别结果: {"label": "cat", "confidence": 0.94, "bbox": [100, 120, 200, 300]}
        │
        ▼ 进程间通信 (Unix Domain Socket: /var/run/json_ipc.socket)
 [ 3. 本地联动 ] 通知 Octopus 主底座做出物理反应
        │       - 小脑控制: 鸭子转头对准猫咪，播放音频叫声
        │       - 状态查询: 获取当前设备电量、GPS/Wi-Fi 信号强度
        │
        ▼ 物联网协议 (MQTT / HTTPS)
 [ 4. 结果上云 ] 将事件元数据（+ 截帧缩略图）打包推送到云端服务器
```

### 3.2 多进程协同系统拓扑图

```text

 └─────────────┬───────────────────────────────┬─────────────────────────────▲────────────┘
               │ 原始视频帧                    │ 硬件推理调用                 │ JSON元数据/图片
```

### 3.3 云端上传的避坑指南
将结果发送给云端通常包含两项数据：**“识别文本元数据”** 和 **“抓拍现场图片”**。

#### (1) 文本元数据走 MQTT 协议（极轻量、低延迟）
当 NPU 检测到画面中出现目标时，发布一条结构化 JSON 消息到 `/duck/ai/events` 主题：
```json
{
  "device_id": "duck_88321",
  "timestamp": 1726000000,
  "event_type": "object_detected",
  "data": {
    "target": "cat",
    "confidence": 0.94,
    "box": [100, 120, 200, 300],
    "image_attached": true
  },
  "device_status": {
    "battery": 88,
    "wifi_rssi": -58
  }
}
```

#### (2) 现场图片上传（严禁 Base64 塞进 MQTT！）
- **错误做法**：把图片转成 Base64 字符串塞进 MQTT JSON 里发送，导致内存严重膨胀，极易引起弱网卡死；
- **工业最佳实践（预签名直传 S3/OSS）**：
  1. AI 进程抓拍后，编码为 JPEG 存入内存 `/tmp/snapshot.jpg`；
  2. 云端收到 MQTT 报警后，下发一个带有短时效的预签名上传地址（Presigned URL，如阿里云 OSS / 腾讯云 COS / AWS S3）；
  3. 机器人调用轻量 HTTP 客户端（如 `libcurl`），直接把二进制流 PUT 到云端对象存储；
  4. 手机 App 直接从对象存储秒级拉取图片，既节省机器人 CPU，又节省流量。

#### (3) 弱网与断网环境设计（离线本地缓存）
- 机器人跑到没有 Wi-Fi 信号的死角（如床底、地下室）：
- `ai_vision_daemon` 识别到目标后，将事件和图片写入 `/data/spool/ai/`。该目录必须设定容量上限（如 20MB）和条数上限，写满后丢弃最旧的数据，而且 JPEG 缩略图的写入频率要受控，否则持续断网时摄像头会把 DATA 分区写满、把 Flash 写穿；
- 一旦恢复联网，Octopus 网络模块广播 `network.online` 事件，触发自动**断网补传**。

#### (4) 隐私与合规
识别“人”并上传截图，属于处理个人信息，需遵守《个人信息保护法》、GDPR 等法规：
- 默认只上传事件元数据，截图上传需用户明确开启；
- 支持在设备端对人脸做打码后再上传，原图不出设备；
- 本地缓存与云端存储都要有明确的保留期限，出厂恢复时清空本地缓存；
- 设备上有明显的“摄像头工作中”指示（如 LED），不能在用户不知情时采集。

### 3.4 AI 模型的差量 OTA 升级（基于 OFI 分段优势）
做视觉识别时，模型迭代极快（今天用某版本权重包，下周升级为针对特定动物训练的 `v2`；具体文件后缀取决于厂商工具链导出格式）。
利用 Octopus 的 **OFI 分段机制**，模型文件独立打包为 **`model.squashfs`**，有两种更新方式（详见架构文档 8.5）：
- **随槽位更新**：OTA 只下载变化的模型段，写入非活动槽时其余段从当前槽拷贝，重启后生效。模型损坏导致系统无法通过健康门槛时，由 U-Boot 的 bootcount 机制回退到旧槽位（连同旧模型）；
- **热更新**：模型包单独签名，写入 `/data/models/` 的非活动目录，只重启 `ai_vision_daemon`。这条路径与 U-Boot 无关，新模型加载失败时由升级服务把指针切回旧目录。
- 注意：U-Boot 只负责引导内核，**不会**加载或检查模型，模型能否正常推理只能由用户态的健康检查判断。

## 4. 接口体系演进：应对现代 AI 与流式交互

传统四大管理接口（WEB、`octopus_cli`、JSON-RPC、SNMP）面向以太网设备配置。在现代 AI 机器人场景下，需要进行明确的**升级与重构**：

### 4.1 传统接口的审视与裁剪
- **SNMP**：在消费级/商用机器人上**完全无用，直接裁掉**（仅在工业特种巡检机型中保留）；
- **octopus_cli**：退化为**内部研发调试、产线电机校准、底层故障诊断**的工程控制台；
- **JSON-RPC**：继续作为**基础配置与状态查询（Request-Response）**的骨干，但无法应对流式与高带宽场景。

### 4.2 面向现代 AI 必须补充的 4 种新接口

```text
 ┌────────────────────────────────────────────────────────────────────────────────────────┐
 │                               现代 AI 机器人的全套交互接口体系                          │
 ├──────────────────────────────────────────┬─────────────────────────────────────────────┤
 │ 原有保留接口 (稳态配置与底座控制)        │ 为 AI / 机器人新增的流式接口                │
 ├──────────────────────────────────────────┼─────────────────────────────────────────────┤
 │  1. octopus_cli (串口/SSH)                      │  ★ 5. WebSocket (双向流式通信)               │
 │     - 产线校准、底层舵机调优、查看内核日志 │     - LLM Token 流式吐字、实时遥测数据毫秒级推送│
 │                                          │                                             │
 │  2. JSON-RPC (HTTP / 本地 Unix Socket)   │  ★ 6. WebRTC (超低延迟音视频流)             │
 │     - 参数配置 (改音量、改Wi-Fi、查电量) │     - 机器鸭第一视角实时图传 (FPV < 200ms)  │
 │     - 本机 AI 进程调小脑电机的控制管道   │     - 手机与鸭子之间的远程双向语音对讲      │
 │                                          │                                             │
 │  3. Web H5 (嵌入式轻量前端)              │  ★ 7. MQTT (云端物联网与大脑下发)           │
 │     - 手机扫码连接热点后的配网页面       │     - 接入云端物联网平台，接收远程远程唤醒  │
 │                                          │                                             │
 │  4. [降级/裁剪] SNMP                     │  ★ 8. DMA-BUF / 共享内存 (零拷贝本地通道)   │
 │     - 消费级裁掉；工业巡检机型才开启     │     - 摄像头采集帧直通 NPU，避免内存拷贝开销│
 └──────────────────────────────────────────┴─────────────────────────────────────────────┘
```

#### 接口 1：WebSocket（解决大模型流式打字机交互）
- **痛点**：传统 JSON-RPC 必须等待整段话生成完才一次性返回，面对大模型（如接入 DeepSeek）对话，机器人会陷入数秒的呆滞；
- **解法**：通过 WebSocket 全双工长连接，云端或本地大模型吐出一个 Token（一个字），机器人就顺着 WS 实时输出一个字，语音合成（TTS）同步流式播报。

#### 接口 2：WebRTC（解决第一视角图传与双向音视频对讲）
- **痛点**：用户打开手机 App 想看机器鸭“眼前的画面”，如果走传统 HTTP 轮询或者 RTSP，延迟高达 1~3 秒且极难穿透内网 NAT；
- **解法**：引入 WebRTC 协议栈，端到端延迟低于 **200 毫秒**，自带 NAT 穿透，并且支持手机与机器人之间的双向低延迟语音对讲，还可通过 DataChannel 发送虚拟遥控手柄指令。

#### 接口 3：MQTT（解决上云与云端大脑控制）
- **解法**：集成轻量级 MQTT 客户端（基于 Eclipse Paho C 库，约几百 KB）。开机联网后与云端 IoT 平台保持长连接，负责心跳保活、AI 事件上报及云端控制下发。

#### 接口 4：DMA-BUF / 共享内存（解决本地视频帧零拷贝传输）
- **痛点**：1080P 原始 YUV/RGB 图像一帧达几兆字节，绝对不能转成 JSON 字符串去走 Socket，否则 CPU 会因内存拷贝直接打满；
- **解法**：使用 Linux 标准的 DMA-BUF（Direct Memory Access Buffer），摄像头驱动直接把图像填入物理内存，进程间仅通过 Unix Socket 传递一个文件描述符（fd），NPU 硬件通过 DMA 直接读取物理内存，**CPU 零拷贝，开销接近 0 毫秒**。

## 5. 终极全景架构总图（AI 机器人/智能视觉网关形态）

将 Octopus 的高可靠性与现代 AI 需求融合后的系统全景图如下：

```text

 │                      外部用户交互层 (手机 App / 网页 / 遥控器 / 研发终端)              │

           │ 手机看监控图传 (WebRTC)│ 手机配网/发指令 (Web/WS)│ 研发调机 (串口/SSH)  │ 云端大模型下发
           ▼                       ▼                        ▼                      ▼
```

## 6. RK3568 硬件算力底账与资源规划

针对瑞芯微 **RK3568**，其硬件规格应对上述需求完全绰绰有余：

| 硬件核心 | 规格与算力指标 | 承担的实际业务与负荷表现 |
| :--- | :--- | :--- |
| **CPU** | 4 核 Cortex-A55 @ 2.0GHz | 运行 Octopus 底座、MQTT 通信、Linux 系统调度，日常占用率通常 **< 15%**。 |
| **NPU** | **1.0 TOPS** (支持 INT8/FP16) | 运行目标检测轻量模型 **YOLOv8n / YOLOv5s-nano**（覆盖人、猫、狗等 80 类常见目标）。推理单帧耗时仅 **25~35ms**，可稳定跑满 **25~30 FPS 实时检测**。 |
| **ISP / VPU** | 4K 硬件解码、RGA 2D 硬件加速 | 硬件完成摄像头画面的裁剪、旋转、色彩空间转换（YUV->RGB），**完全不耗费 CPU 算力**。 |
| **内存开销** | 建议标配 2GB 或 4GB LPDDR4 | Octopus 底座内存约 **20~30MB**；AI 运行时 + 模型权重约 **80~120MB**；系统整体运行极度从容。 |

## 7. 总结

1. **架构契合度极高**：通过将 Octopus 定位为“稳态小脑与管家”，将 AI 推理隔离在“独立受护大脑”，兼顾了工业级的抗死机稳定性和现代 AI 视觉的灵活性；
2. **落地抓手清晰**：底层沿用 OFI 分段、A/B 分区、octopus_config 存盘和 Unix Socket 通信；外围仅需扩展 WebSocket、WebRTC 和 MQTT，即可轻松孵化出高可靠的商用级智能机器人产品！
