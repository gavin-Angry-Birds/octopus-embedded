# 交换芯片 SDK 层解析与第三方内核驱动（.ko）接入架构指南

**简体中文** | [English](./02-switch-hal-drivers.en.md)

> **文档定位**：针对嵌入式开发者在构建 Octopus Embedded 通用底座时最容易混淆的 **交换芯片 SDK 与 Linux 内核驱动（.ko）的关系** 进行说明。深入阐明硬件驱动在不同业务场景下的标准接入通道与生命周期管理机制。

---

## 1. 核心概念辨析：交换芯片 SDK 究竟是什么？

首先必须明确一条根本原则：**交换芯片 SDK 全部运行在 Linux 用户空间（User Space），它们是纯粹的 C/C++ 语言函数库，根本不是内核模块（.ko）！**

```text
 ┌────────────────────────────────────────────────────────┐
 │ octopus_app (用户态核心进程)                            │
 ├────────────────────────────────────────────────────────┤
 │ 交换芯片 SDK (Switch SDK) - 用户态 C 库     │ 负责“芯片级”通用逻辑
 ├────────────────────────────────────────────────────────┤
 │ 板级交换适配层 (Board Adaptation Layer)  - 用户态 C 库     │ 负责“板级硬件差异”适配
 └──────────────────────────┬─────────────────────────────┘
                            │ 通过 UIO /dev 节点或字符设备交互
 ┌──────────────────────────▼─────────────────────────────┐
 │ Linux 内核空间 (Kernel Driver / .ko 驱动层)            │
 └────────────────────────────────────────────────────────┘
```

### 1.1 交换芯片 SDK（芯片层通用 API，纯软件抽象）
- **归属**：由交换芯片厂商提供，通常以私有 SDK 形式授权，不在本仓库中分发。
- **职责**：它只认识**交换芯片核心本身**（如工业千兆交换芯片、万兆多口以太网芯片等），完全不关心芯片焊在什么板子上。
- **业务范畴**：芯片内部功能的通用抽象，例如：
  - “在 MAC 地址表中插入/删除静态条目”；
  - “创建 VLAN 10 并把 1~4 号物理端口加为成员”；
  - “配置端口限速队列与 QoS 策略”；
  - “设置全局链路聚合（LACP）控制参数”。

### 1.2 板级交换适配层（板级差异适配层，电路板的“翻译官”）
- **归属**：由板卡厂商或产品团队按板子编写，位于 `plugins/switch_offload/boards/`，随可选插件编译。
- **痛点**：同样一颗交换芯片，不同的硬件厂商会画出形态迥异的电路板：
  - A 厂商画的是 24 口全光口板，SFP 光模块接在 CPU 的 I2C-1 总线上，LED 状态灯由 GPIO 5 控制；
  - B 厂商画的是 8 口电口板，外挂了特定型号的 PHY 芯片，PHY 地址是 `0x10`，复位引脚接在移位寄存器上；
  - C 厂商画的是工控板，要求支持外部硬件看门狗喂狗和特定电源芯片监测。
- **职责**：板级交换适配层（Board Switch Adaptation，代码前缀 `bsa_`）就是为每块具体的板子实现一套回调函数（如 `bsa_board_rk3568_custom.c`）。
- **工作机制**：上层调用 `bsa_port_admin_state_set(port, enable)` 时，板级交换适配层 内部负责去操作具体的 GPIO 引脚使能供电，或者通过 Linux I2C 节点配置光模块。

## 2. 交换芯片方案是怎么通过 `.ko` 驱动操作硬件的？（特殊的高性能设计）

在传统的 Linux 体系中，网络通信走的是标准的内核网络设备驱动（`struct net_device`，如 `e1000.ko`、`r8169.ko`）。数据包经过内核网络协议栈（`sk_buff`）处理。

但在企业级以太网交换机中，由于有几十个千兆/万兆端口，如果所有的线速报文都走 Linux 内核，CPU 会立即被打满瘫痪。因此部分高性能网络设备方案采用**反传统的旁路直通设计**。

> 这是一种可选方案，而非 Octopus 的默认路径。Octopus 以 Linux 内核 FIB 为唯一真实源（RFC-06），首选 DSA / switchdev 内核驱动；只有交换芯片没有主线内核驱动时，才退回下面的 UIO + 用户态 SDK 方式，并作为 `switch_offload` 插件隔离。UIO 方案下，端口不再是标准 netdev，FRR、iptables 等依赖内核网络栈的生态无法直接使用，这正是 RFC-06 要避免的。

```text
 [ 用户态主进程 ]
   octopus_app (包含 交换芯片 SDK)
       │
       │ 1. open("/dev/uio0")
       │ 2. mmap() 将交换芯片寄存器映射到自己的虚拟内存
       ▼
 ┌────────────────────────────────────────────────────────┐
 │ Linux 内核空间                                         │
 │                                                        │
 │   加载轻量驱动: switch_uio.ko (基于原生 Linux UIO 框架)   │
 │   职责：仅负责导出物理寄存器内存区域给用户态，不做业务逻辑 │
 └────────────────────────────┬───────────────────────────┘
                              │
                              ▼
 ┌────────────────────────────────────────────────────────┐
 │ 物理硬件: 以太网交换芯片物理寄存器空间                 │
 └────────────────────────────────────────────────────────┘
```

1. **极其纯粹的 UIO 驱动**：内核只加载一个极小的驱动 `switch_uio.ko`（几 KB 大小）；
2. **内存直接映射**：主程序启动时，通过 `open("/dev/uio0")`，调用 `mmap()` 把交换芯片所有的控制寄存器地址空间直接拉进用户态内存；
3. **性能极致**：交换芯片 SDK 在用户态配置硬件时，本质上就是直接向这片内存指针写寄存器，**零系统调用开销，零内核态切换**。

## 3. 当用户有自己特殊的 `.ko` 驱动时，究竟该怎么接入？

开发者往往疑惑：*“如果我的硬件板子上接了自己的特殊硬件（比如专用 FPGA、特殊的 SFP 控制器、加密芯片），写了内核驱动 `.ko`，我该找谁？怎么交互？”*

根据硬件的业务归属，架构上有 **三大标准场景**：

---

### 场景 1：用户驱动属于“以太网网络外设”（必须对接 板级交换适配层）

> **典型案例**：客户做了一块定制交换板，板上外挂了特殊的 **SFP 光模块供电芯片**，或者某种特殊的 **以太网 PHY 芯片**。客户编写了专属的内核驱动 `my_sfp_ctrl.ko`，加载后生成了字符设备 `/dev/sfp_ctrl`，通过 `ioctl` 控制光模块使能。

**接入机制与代码流向**：
这种硬件属于以太网端口体系的一部分，因此**必须在 板级交换适配层代码中对接**。

```text
 ┌──────────────────────────────────────────────┐
 │ octopus_app 核心业务逻辑                      │
 └──────────────────────┬───────────────────────┘
                        │ 调用标准 API: bsa_port_admin_state_set(port, enable)
                        ▼
 ┌──────────────────────────────────────────────┐
 │ 板级交换适配层代码 (如 bsa_custom_board.c)   │
 │                                              │
 │  /* 在 板级交换适配层 回调中操作客户特殊的字符设备 */ │
 │  int fd = open("/dev/sfp_ctrl", O_RDWR);     │
 │  ioctl(fd, SFP_CMD_ENABLE_POWER, &port);     │
 │  close(fd);                                  │
 └──────────────────────┬───────────────────────┘
                        │ VFS 系统调用 (open/ioctl)
                        ▼
 ┌──────────────────────────────────────────────┐
 │ Linux 内核: 客户的驱动 (my_sfp_ctrl.ko)       │
 │ 生成设备节点: /dev/sfp_ctrl                  │
 └──────────────────────┬───────────────────────┘
                        │ 扳动硬件引脚
                        ▼
 ┌──────────────────────────────────────────────┐
 │ 物理硬件 (SFP 控制器 / 光模块供电)           │
 └──────────────────────────────────────────────┘
```

- **架构收益**：上层的 交换芯片 SDK 和 `octopus_app` 业务代码完全不用改动，保持纯净；硬件差异被完全封死在 板级交换适配层 这一个板级文件里。

---

### 场景 2：用户驱动属于“通用工业/业务外设”（完全脱离 交换芯片 SDK！）

> **典型案例（重要认知突破）**：  
> 客户使用 RK3568 或 SSD20X 开发边缘网关产品，板子上接了一块 **FPGA 数据采集卡**、**国密硬件加密芯片**、或者 **多路 RS485 拓展串口芯片**。客户自行编写内核驱动 `my_fpga.ko`（属客户工程，不进入 Octopus 本仓库），生成 `/dev/my_fpga0`。

**关键认知突破**：  
**此时根本不需要经过 板级交换适配层 和 交换芯片 SDK！**  
板级交换适配层 和 交换芯片 SDK 的职责边界仅限于以太网网络。对于通用的工业硬件外设，Octopus 底座提供了两条极简、高效的接入通道：

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                             客户硬件方案                               │
 │             (例如：FPGA 数据采集卡，带有 my_fpga.ko 驱动)              │
 └──────────────────────────────────┬─────────────────────────────────────┘
                                    │ insmod 生成设备节点 /dev/my_fpga0
                                    ▼
       ┌────────────────────────────────────────────────────────────┐
       │                 用户层怎么选择接入方式？                   │
       └──────────────┬──────────────────────────────┬──────────────┘
                      │ 方式 A: In-Tree (高性能模式) │ 方式 B: Out-of-Tree (松耦合模式)
                      ▼                              ▼
 ┌─────────────────────────────────────────┐  ┌─────────────────────────┐
 │ 在 Octopus 核心底座内写一个模块:        │  │ 客户编写独立的外部进程: │
 │ modules/fpga_mgr/                       │  │ /usr/bin/fpga_daemon    │
 │  - 直接 open("/dev/my_fpga0") 读写数据  │  │  - 自由读写 /dev/my_fpga0│
 │  - 注册结构体到 JSON-RPC 方法树         │  │  - 调 Unix Socket       │
 │  - 自动获得 Web API / CLI 命令行 / octopus_config │  │    /var/run/            │
 │    配置断电自动存盘                     │  │    json_ipc.socket      │
 └─────────────────────────────────────────┘  └─────────────────────────┘
```

#### 方式 A：In-Tree 模式（与底座高内聚，一步到位获得全套管理面）
- **做法**：在 Octopus 的 `modules/` 目录下新增一个模块（如 `modules/fpga_mgr/`）；
- **操作**：在模块的 C++ 业务线程中直接调用 `open("/dev/my_fpga0", O_RDWR)` 进行日常读写；
- **巨大红利**：只要用 `StructReadWrite` 模板将采集到的参数登记一次：
  1. **Web 界面** 自动获得查询和配置该 FPGA 的 Ajax 接口；
  2. **octopus_cli 控制台** 自动获得 `show fpga status` 类似命令；
  3. **octopus_config 配置存盘** 自动支持断电保存参数，开机自动恢复。

#### 方式 B：Out-of-Tree 模式（独立外部进程，零风险隔离）
- **做法**：客户不改动 Octopus 主程序的一行源码，自己用 C/C++/Python 写一个独立的 Linux 守护进程（如 `/usr/bin/fpga_daemon`）；
- **操作**：该进程独占 `/dev/my_fpga0` 进行高频数据采集；当需要把状态同步给系统、或者接收 Web 下发的参数时，通过调用轻量的 `liboctopus_client`，与本地的 `/var/run/json_ipc.socket` 通信；
- **巨大红利**：**完全容错隔离**。哪怕客户的这个驱动写得有 Bug 导致子进程段错误退出，Octopus 主进程依然稳如磐石，octopus_supervisor 还会立刻把退出的子进程重新拉起自愈！

---

### 场景 3：驱动的生命周期——`.ko` 是由谁加载的？什么时候加载？

很多工程师对 OFI、两阶段引导（initramfs/rootfs）、SquashFS 和 OverlayFS 的文件系统环境感到困惑，不知道驱动应该放在哪里、何时生效。

在 Octopus 标准启动流中，内核驱动的加载生命周期如下：

```text
                   U-Boot 引导 initramfs (Kernel + 极简 Initramfs)
                                       │
                                       ▼
                   initramfs 阶段运行 octopus_loader，挂载根文件系统
                   (只读 SquashFS + 可写 OverlayFS 叠加合成)
                                       │
                                       ▼
                   【关键时刻：rootfs 就绪后 exec /sbin/octopus_supervisor (PID 1)】
                                       │
                                       ├─► 步骤 1: octopus_supervisor 优先执行内核驱动加载服务
                                       │           服务定义: /etc/octopus/services.d/kmod.conf
                                       │           模块清单: /etc/octopus/modules.list
                                       │           ─────────────────────────────────────────
                                       │           ① 加载 Linux 基础驱动:
                                       │              modprobe uio
                                       │              modprobe i2c-dev
                                       │           ② 加载用户自定义业务驱动:
                                       │              modprobe my_fpga (模块放在 extra/ 并执行过 depmod)
                                       │           ─────────────────────────────────────────
                                       │           ==> 此时 /dev/my_fpga0 设备节点正式生成！
                                       │
                                       ├─► 步骤 2: 驱动就绪后，octopus_supervisor 再按依赖拉起应用服务
                                       │           - 拉起 /usr/bin/octopus_app (主进程)
                                       │           - 拉起 /usr/bin/fpga_daemon (客户独立进程)
                                       ▼
                   主应用与客户进程安全 open("/dev/my_fpga0")，业务正常启动！
```

- **存放路径**：用户的 `.ko` 驱动文件打包进 `rootfs.squashfs`，固定存放在 `/lib/modules/$(uname -r)/extra/` 目录下，构建时执行 `depmod`。根文件系统只读，模块不能在运行时拷贝进去，只能随 OFI 升级；
- **加载配置**：在 `/etc/octopus/modules.list` 中追加一行模块名即可，由 supervisor 的 `kmod` 服务按顺序 `modprobe`。依赖该驱动的服务在自身定义中声明 `after = kmod`，不要再写 `sleep` 等待设备节点；
- **内核版本绑定与签名**：`.ko` 必须与内核版本、配置严格匹配，内核升级时要一起重新编译并放进同一个 OFI。开启内核模块签名（`CONFIG_MODULE_SIG_FORCE`）时，第三方驱动需用同一把密钥签名，否则拒绝加载。这是 Secure Boot 信任链在内核之后的延续。

## 4. 总结与决策速查表

| 硬件外设分类 | 典型代表 | 是否需要 交换芯片 SDK？ | 驱动操作与交互位置 |
| :--- | :--- | :--- | :--- |
| **以太网交换芯片** | 工业级/企业级以太网交换芯片 | **按需加载** | 内核加载 `switch_uio.ko` 或 DSA 驱动；交换芯片驱动在用户态通过 `mmap` 直接读写硬件物理寄存器或由内核接管。 |
| **交换机板级端口外设** | 端口 SFP 光模块、外挂 PHY 芯片、端口状态 LED 灯 | **必须需要** | 驱动在内核生成 `/dev/i2c-*` 或字符设备；**在 板级交换适配层 的板级适配源码中** 写 `open/ioctl` 驱动硬件。 |
| **通用工业业务硬件** | FPGA 采集卡、加密芯片、多路串口芯片、ADC 采样芯片 | **完全不需要！** | 内核正常加载 `my_hw.ko` 生成 `/dev/my_hw`。<br>用户可在 **Octopus In-Tree 模块** 或 **外部独立子进程** 中按标准 POSIX API 直接 `open` 操作。 |

## 5. 架构核心思考：我们究竟需不需要一个用户态 HAL 层？

在理清了 交换芯片 SDK 和内核驱动的边界后，很多开发者会产生一个深层疑问：  
**“既然要跨芯片平台（RK3568、SSD20X、全志），那 Octopus 是不是需要像 Android 一样，在用户态写一套庞大的通用硬件抽象层（HAL，如 GPIO_HAL、I2C_HAL、UART_HAL）？”**

**核心结论：不是不需要 HAL，而是“Linux 内核本身就已经是绝大多数通用硬件的终极 HAL”！我们绝不能在用户态重复造轮子。**

---

### 5.1 为什么通用外设不需要用户态 HAL？（Linux 内核就是天然的 HAL）

在嵌入式 Linux 体系中，**“内核驱动框架 + 设备树（Device Tree, DTS）”** 已经构成了业界最规范、跨芯片最彻底的硬件抽象层：

```text
               Octopus 应用层 (业务主程序)
                 │
                 │ 面对的是完全跨芯片、通用的 POSIX / Linux VFS 标准接口:
                 │  - 串口通信: /dev/ttyS0, /dev/ttyFIQ0 (标准 termios API)
                 │  - 网卡配置: eth0, eth1 (标准 Linux Socket / Netlink / ioctl API)
                 │  - I2C 总线: /dev/i2c-1 (标准 i2c-dev ioctl API)
                 │  - 硬件看门狗: /dev/watchdog (标准 Linux Watchdog API)
                 │  - 块设备与分区: /dev/mmcblk0, /dev/mtd0
                 ▼
 ┌────────────────────────────────────────────────────────┐
 │           Linux 内核本身就是天然的终极 HAL             │
 ├────────────────────────────────────────────────────────┤
 │ 瑞芯微 RK3568   │  星宸 SSD20X   │  全志 T507 / H616   │
 │ 设备树 (.dts)   │  设备树 (.dts) │  设备树 (.dts)      │
 └─────────────────┴────────────────┴─────────────────────┘
```

#### 真实案例对比：
- 在 **RK3568** 上，I2C-1 控制器物理基地址是 `0xFE5A0000`，引脚是 `GPIO0_B3`；
- 在 **SSD20X** 上，I2C-0 控制器物理基地址是 `0x1F220000`，引脚是 `PAD_I2C0_SCL`；
- **差异在哪里被抹平？** 在各自芯片的 **内核驱动源码与板级设备树（DTS）** 中被消化！
- **应用层看到了什么？** 两款芯片的应用层看到的都是标准的 `/dev/i2c-0` 设备文件。应用层直接使用 `open()`、`read()`、`write()` 即可，**根本不需要在应用层再包一层所谓的 `i2c_hal_read()`**。

---

### 5.2 为什么早期部分方案在用户态造了交换芯片 SDK / 板级交换适配层？

这是因为早期交换芯片方案为了追求极致性能，干了一件**“反传统”**的事：
为了让以太网交换芯片达到数十 Gbps 的硬件线速转发，它**彻底抛弃了 Linux 内核网络驱动框架（`struct net_device`）**，直接用 UIO 将芯片的物理寄存器映射到了用户空间。

**由此带来的副作用：**
既然你主动放弃了 Linux 内核驱动，那么 Linux 内核原本为你准备好的一切抽象能力（如 netdev 抽象、PHY 状态机抽象、MDIO 总线抽象）就**全部失效了**！
因此，厂商不得不在用户态硬生生自己重造了一套 HAL：
1. **交换芯片 SDK**：交换芯片寄存器抽象层（芯片级用户态 HAL）；
2. **板级交换适配层**：各个交换板卡的引脚与光口/PHY 芯片抽象层（板级用户态 HAL）。

---

### 5.3 在 Octopus 通用底座中，我们究竟需要怎样的 HAL？

基于上述原理，Octopus 确立了清晰的 HAL 架构哲学：

> **核心原则：**  
> 1. **绝不重复造 Linux 已有的驱动抽象轮子**（UART、I2C、SPI、Watchdog、标准网卡直接走 Linux 内核标准接口）；  
> 2. **仅保留一个“极轻量的板级差异适配接口（Board HAL）”**，专门处理那几件 Linux 内核没有统一定义的“板级杂事”。

这几件“板级杂事”通常仅限于以下 4 项：

```text
                       Octopus 核心业务层
                               │
                               ▼
 ┌────────────────────────────────────────────────────────────┐
 │         Octopus 极轻量板级适配层 (Board HAL)               │
 ├────────────────────────────────────────────────────────────┤
 │ 1. 唯一设备身份读取 (board_get_mac / board_get_serial_no) │
 │ 2. 出厂重置按键检测 (board_is_factory_reset_triggered)     │
 │ 3. 系统状态指示灯   (board_set_status_led)                │
 │ 4. [可选插件] 交换网络底层适配 (板级交换适配层 接口)                 │
 └─────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
        底层的具体实现（各板卡写一个独立的 .c 适配文件）
```

#### 为什么只有这几件事需要 Board HAL？
以**“获取设备的出厂物理 MAC 地址与序列号”**为例：
- 在 **RK3568 工控板** 上：MAC 地址可能烧录在 CPU 内部的 OTP / Efuse 区域，或者从 eMMC CID 算出来；
- 在 **SSD20X 核心板** 上：MAC 地址存放在外挂 I2C EEPROM 的 `0x00~0x05` 偏移量处；
- 在 **全志网关主板** 上：MAC 地址保存在 SPI NAND Flash 专用的 `factory` MTD 分区内。

业务层（网络配置模块、Web 状态展示）只需要知道设备的物理 MAC 究竟是多少，它**绝不应该关心当前板子究竟是从 EEPROM 读出来的还是从 Efuse 读出来的**。

因此，在 Octopus 中只需要提供一个极其简洁小巧的板级 C 接口。下面是说明思路的**简化示意**，实际接口以架构文档 6.2 冻结的 `board_hal.h`（位于 `liboctopus_board`）为准：

```c
// 示意代码，非正式接口

typedef enum {
    LED_SYS_RUN,
    LED_SYS_ALARM,
    LED_SYS_CLOUD
} board_led_id_t;

typedef enum {
    LED_OFF,
    LED_ON,
    LED_BLINK_SLOW,
    LED_BLINK_FAST
} board_led_state_t;

typedef struct {
    // 1. 读取主板出厂硬编码的 MAC 地址
    int (*get_factory_mac)(uint8_t mac_out[6]);
    
    // 2. 读取主板序列号 (SN)
    int (*get_serial_number)(char *sn_out, size_t max_len);
    
    // 3. 控制系统运行状态指示灯
    void (*set_status_led)(board_led_id_t led, board_led_state_t state);
    
    // 4. 检测是否长按了出厂恢复物理按键 (Reset Button)
    //    正式接口为 octopus_board_factory_reset_triggered()（长按判定与 LED 反馈在 HAL 内），
    //    此处名称仅为本节的示意写法，以架构文档 6.2 为准
    bool (*is_factory_reset_triggered)(void);
} octopus_board_ops_t;

// 注册当前板卡的实现
int octopus_board_register(const octopus_board_ops_t *ops);
```

对于具体的板子：
- 为 RK3568 写一个 `board_rk3568_evb.c`（里面用 Efuse 读 MAC，用 Linux `gpio-keys` 读按键）；
- 为 SSD20X 写一个 `board_ssd20x_gw.c`（里面用 I2C 读 EEPROM 获得 MAC）；
- 上层主程序完全感知不到板卡硬件差异，核心代码极度清爽。

## 6. 对 Octopus 通用架构设计的指导意义

1. **边界清晰，绝不滥用 交换芯片 SDK**：  
   在打造跨芯片平台（RK3568、SSD20X、全志）的通用底座时，不要把非网络相关的代码往 交换芯片 SDK 里面塞。交换芯片 SDK 应被完全隔离在可选插件包 `plugins/switch_offload/` 之中。如果硬件没有专用的 以太网交换 ASIC，直接关掉编译宏即可，底座依然完整。
2. **坚持标准 Linux 哲学**：  
   对于用户的各类扩展外设，内核负责通过驱动提供标准的字符设备节点（`/dev/xxx`）；Octopus 负责在用户态提供极致便捷的接入框架（In-Tree 自动生成 Web/CLI，Out-of-Tree 提供高速 IPC Socket）。
3. **极简 Board HAL 足够好**：  
   不写冗长重型的用户态驱动封装，仅保留轻量的 `board_hal` 消化 MAC/SN、状态灯、复位键差异，让整个软件框架既高内聚，又极易在不同芯片间快速迁移！
