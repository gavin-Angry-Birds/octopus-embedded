## 议题 1：配置生命周期、版本迁移与出厂恢复机制（Persistence & Lifecycle）

系统的配置持久化（Running-Config / Startup-Config）基于纯文本 octopus_config 格式存放在 Flash 的可写持久化数据分区中。在产品长达数年的生命周期中，已确立以下三项核心工程技术规范：

### 1.1 跨固件版本的配置迁移规范（Schema Migration）
- **问题与挑战**：
  设备从 V1.0 升级到 V2.0 固件后重启。V2.0 固件中某些业务模块增加了新的参数，修改了参数的默认值范围，或者废弃了旧版参数名。
- **已敲定实施规范：宽容解析 + 缺省兜底 + 版本元数据**：
  1. **首行版本元数据**：octopus_config 序列化生成的文件首行强制包含版本标记（如 `!version 1.0.4`），用于标识生成该配置的固件版本；
  2. **宽容重放解析（Tolerant Parsing）**：主应用在重放旧配置时，若解析器遇到不认识的旧命令或已废弃语法，**记录一条 Syslog 警告日志并自动跳过**，继续解析下一行，绝不阻断系统启动；
  3. **缺省出厂值兜底**：对于新固件新增的配置字段，若旧配置文件中未包含该行，业务模块自动采用当前固件源码内置的出厂默认值，实现 100% 平滑向后兼容与平稳开机。

---

### 1.2 出厂恢复（Factory Reset）的分级定义与触发路径
- **关键边界与触发路径（已敲定采用 Linux 用户态检测 + 视觉反馈）**：
  1. **软恢复**：在 Web 界面、octopus_cli 命令行敲入 `factory-default` 命令，主应用安全清空配置并触发重启；
  2. **硬恢复（物理按键）**：
     - **检测时机**：在设备正常启动进入 Linux 后，由主底座的 `liboctopus_board` 模块注册物理轻触按键的 GPIO 中断，并启动防抖软件定时器；
     - **长按判定**：用户持续按压达 **5 秒** 判定为触发恢复出厂；
     - **视觉反馈**：长按期间及触发瞬间，通过系统双色 LED 以急促高频闪烁（或红绿交替跑马灯）给出明确的用户视觉反馈，提示用户“出厂恢复确认，即将重启”，防止意外误触。
  3. **启动早期恢复（兜底路径）**：只在 Linux 用户态检测按键有一个盲区：如果恰恰是某条配置让 `octopus_app` 启动即崩溃，设备永远走不到按键检测那一步。因此 U-Boot 也要在上电时读取同一个按键：按住按键上电超过 N 秒，U-Boot 在 bootargs 中加入 `octopus.factory_reset=1`，由 Loader 在挂载 `/data` 之前完成清空。配合 supervisor 的“连续崩溃计数”，也可以在连续多次启动失败后自动以出厂配置启动一次（不删除用户配置，只是不加载）。
- **数据清空范围与“绝对保护红线”**：
  - **彻底清空项（用户私有数据）**：
    - `/data/config/startup-config*`（用户自定义配置）；
    - `/data/log/*`（系统历史运行日志与崩溃转储）；
    - 用户上传的临时脚本或业务数据；
  - **绝对禁止擦除项（设备出厂硬件基因）**：
    - 物理 MAC 地址、设备唯一序列号（SN）、PCB 硬件版本号；
    - 机器人舵机/电机的产线物理零点偏置校准参数（Calibration Data）；
    - 云端预置的设备根证书与出厂密钥；
  - **恢复后的状态**：主应用检测到用户配置文件不存在，自动加载并重放刷在根文件系统只读层里的黄金出厂只读配置（`default-config`），恢复默认 IP（如 `192.168.1.1`）。登录密码恢复为**该设备唯一的初始密码**（产线写入 FACTORY、印在铭牌上），而不是所有设备共用的默认密码，后者已被 ETSI EN 303 645、欧盟 CRA 等法规禁止；
  - **现场重新校准**：更换舵机或电机后需要重新校准，但 FACTORY 分区只读。现场校准值写入 `/data/calib/`，读取时优先于 FACTORY 中的产线值；出厂恢复会删除现场校准，回到产线值。

### 1.3 突发掉电下的配置文件原子写入规范（Power-loss Atomicity）
- **掉电损坏风险**：
  若直接对目标文件 `open("startup-config", "w")`，在 Flash 擦写磁道的这数毫秒瞬间突发断电，会导致目标文件内容被清空或产生碎片乱码，开机解析彻底损坏。
- **已敲定落地规范：POSIX 原子替换 + 镜像备份双保险**：
  ```text
             【用户或系统触发保存配置】
                        │
                        ▼
   1. 写入临时文件: open("/data/config/startup-config.tmp", O_CREAT|O_WRONLY|O_TRUNC)
                        │
                        ▼
   2. 强制物理刷盘: fsync(fd)，然后 close(fd)（文件末尾带 CRC32 + 长度校验尾）
                        │
                        ▼
   3. 保留上一版:    rename("startup-config", "startup-config.bak")
                        │
                        ▼
   4. POSIX 原子替换: rename("startup-config.tmp", "startup-config")
                        │
                        ▼
   5. 目录落盘:      fsync(/data/config 目录 fd)
                      (rename 只保证原子，不 fsync 目录则掉电后可能回到改名前)
  ```
  加载时依次尝试 `startup-config` → `startup-config.bak` → `default-config`，以校验尾判断文件是否完整。详细规则与“提交与落盘分离、写入合并”的要求见架构文档 7.4。

## 议题 2：硬件看门狗联动、OOM 防护阶梯与崩溃黑匣子（Reliability & Faults）

单靠进程级的 octopus_supervisor 监控不足以应对整个嵌入式系统的异常死锁和硬件失控，必须建立闭环的硬软件兜底机制。本议题确立系统级异常自愈、内存兜底与死机诊断的完整技术规范。

### 2.1 硬件看门狗（Hardware Watchdog）的看护权与“防伪喂狗”模型

#### (1) 传统嵌入式看门狗的三大反模式与陷阱
1. **反模式 A（内核代为喂狗）**：让内核一直替用户态喂狗（例如开启 `CONFIG_WATCHDOG_HANDLE_BOOT_ENABLED` 却不设置 `watchdog.open_timeout`，或者使用软件定时器驱动的“看门狗”）。当用户态核心主进程 `octopus_app` 发生死锁时，内核调度依然正常，看门狗永远不会超时，整机假死却永不复位。注意 `CONFIG_WATCHDOG_NOWAYOUT` 的含义恰好相反：它禁止任何方式关闭已启动的看门狗，是 Octopus **要求开启**的选项；
2. **反模式 B（单线程无脑循环喂狗）**：在 `octopus_app` 内部开一个独立线程 `while(1) { write(wdt_fd); sleep(5); }`。一旦其他工作线程（如网络收发、IPC 处理、电机驱动）因互斥锁死锁挂起，该喂狗线程仍然在独自欢快喂狗，系统依然假死；
3. **反模式 C（无序抢占）**：系统里既有 Busybox 的 `watchdogd`，主进程又去写 `/dev/watchdog`，导致多个进程互相干扰。

#### (2) Octopus 落地规范：主进程独占 + 子系统多维健康心跳矩阵（Heartbeat Matrix）

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                      核心主进程 (octopus_app)                          │
 │                                                                        │
 │  ┌───────────────────────┐   心跳汇报   ┌───────────────────────────┐  │
 │  │ 线程 1: IPC 处理线程  │ ──────────> │                           │  │
 │  └───────────────────────┘ (每2秒tick) │                           │  │
 │  ┌───────────────────────┐   心跳汇报   │   看门狗巡检管理模块      │  │
 │  │ 线程 2: 网络/路由管理 │ ──────────> │   (Watchdog Supervisor)   │  │
 │  └───────────────────────┘ (每2秒tick) │                           │  │
 │  ┌───────────────────────┐   心跳汇报   │   - 维护所有模块的心跳时间戳│  │
 │  │ 线程 3: 控制/业务引擎 │ ──────────> │   - 检查系统整体死锁状态  │  │
 │  └───────────────────────┘ (每2秒tick) │                           │  │
 │                                        └─────────────┬─────────────┘  │
 └──────────────────────────────────────────────────────┼─────────────────┘
                                                        │ 仅当所有子模块健康时
                                                        │ 每 5 秒写入一次
                                                        ▼
                                           ┌──────────────────────────┐
                                           │  硬件看门狗: /dev/watchdog│
                                           │  (超时窗口设为 20 秒)    │
                                           └──────────────────────────┘
```

- **实施细则**：
  1. **独占权控制**：系统启动后，由 `octopus_app` 独占打开 `/dev/watchdog`，设置硬件超时时间为 **20 秒**（禁止其他任何外部程序触碰此设备节点）；
  2. **健康令牌注册**：核心模块（如 IPC 线程、主事件循环、关键驱动线程）在初始化时向看门狗管理器注册“健康令牌”；
  3. **心跳打卡**：每个模块在完成一次正常事件循环后，必须更新自己的时间戳（`heartbeat_tick(MODULE_ID)`）；
  4. **全员健康才喂狗**：看门狗管理线程每 5 秒遍历一次所有模块：**只有所有关键模块的更新时间都在 10 秒以内，才执行一次 `ioctl(WDIOC_KEEPALIVE)` 喂狗**；
  5. **死锁惩罚与硬件复位**：任何一个关键模块心跳超过 10 秒未更新（与架构文档 9.2 的统一时间线一致），看门狗线程立即停止喂狗，并尝试将死锁上下文写入 pstore/日志，随后等待硬件看门狗在 20 秒到达时强行发出硬件复位信号（RESET 引脚拉低），彻底复位整个 SoC；
  6. **正常重启不关闭看门狗**：内核开启 `CONFIG_WATCHDOG_NOWAYOUT`，Magic Close（写入 `'V'`）无效。执行 `reboot` 或 OTA 重启时，`octopus_app` 把超时改为关机流程所需的上限（如 60 秒）后继续保持看门狗运行。关机过程中卸载文件系统卡死、驱动卡死，都能由看门狗兜底复位；如果为了“避免误判”先关掉看门狗，一次关机卡死就会让无人值守设备永远停在那里；
  7. **启动阶段的覆盖**：U-Boot 开启硬件看门狗，内核以 `CONFIG_WATCHDOG_HANDLE_BOOT_ENABLED` 在用户态接管前代为喂狗，并用 `watchdog.open_timeout=` 限定接管期限。这一段不覆盖，A/B 回退中“启动挂死 → 看门狗复位 → bootcount 累加”这条路径就不成立；
  8. **外置看门狗**：部分 SoC 内置看门狗复位不彻底（外设、PMIC 未复位），或者复位后 DDR 内容丢失导致 pstore 失效。高可靠机型建议外置独立看门狗芯片（GPIO 喂狗、直接拉 PMIC 复位），由 Board HAL 的 `octopus_board_wdt_*` 屏蔽差异。

### 2.2 Linux OOM-Killer（内存耗尽杀手）保护阶梯

在内存资源有限的设备上（SSD20X 仅 64~128MB RAM，RK3568 若运行 AI 视觉也有突发开销），一旦物理内存耗尽，Linux 内核会启动 OOM-Killer 随机杀进程。如果杀掉了核心管理进程或 PID 1，系统将瞬间瘫痪。

#### (1) 阶梯配置方案（通过 `/proc/<pid>/oom_score_adj` 控制，范围 -1000 到 +1000）

```text
  【保活级别】                  【进程对象】                     【oom_score_adj 取值】
  ════════════════════════════════════════════════════════════════════════════════
  最高特权 (绝对不可杀) ────>  octopus_supervisor (PID 1)      (无需设置：内核从不选择 PID 1)
                              octopus_app (核心主底座)       -1000 (保活中枢；须配合自身内存上限自检)
  ────────────────────────────────────────────────────────────────────────────────
  标准服务 (中等优先级) ────>  dropbear (SSH), hiawatha (Web)     0 (正常参与内核计算)
                              zebra / ospfd (动态路由)           0
  ────────────────────────────────────────────────────────────────────────────────
  牺牲容灾 (优先被牺牲) ────>  ai_vision_daemon (NPU 视觉)     +500 (内存占用大，优先牺牲)
                              客户自研第三方外部子进程          +700 (防止客户程序拖垮底座)
```

#### (2) 闭环自愈联动
当内存突发暴涨触发 OOM 时，内核会优先杀掉占用数十兆内存的 `ai_vision_daemon` 或客户外部进程，瞬间释放大量物理内存，保住 `octopus_app` 和系统的存活；随后，PID 1 的 `octopus_supervisor` 捕获到子进程退出信号（`SIGCHLD`），在物理内存回落后自动重新拉起 AI 视觉进程，实现**“局部牺牲、系统不倒、秒级自愈”**。

### 2.3 死机黑匣子与现场转储（Crash Diagnostics & PStore）

工业设备部署在野外，一旦设备因段错误（SIGSEGV）或硬件看门狗复位，如果重启后没有任何日志留存，排查问题就成了无头悬案。

#### (1) DDR 尾部保留 1MB 专用内存（RAMoops）
在设备树（DTS）中配置一段保留内存（Reserved Memory），例如物理内存尾部的 1MB 空间，标记为不参与内核动态分配。下例地址对应 4GB DDR 的 64 位平台，1GB / 2GB 机型、32 位 SoC（`#address-cells = <1>`）必须按实际内存布局改写。

**前提条件需要逐板验证**：热复位（Warm Reset / Watchdog Reset）期间 DDR 必须保持自刷新不掉电，而且 SPL、U-Boot、TF-A 都不能使用或清零这段内存。有些板子的看门狗复位会带动 PMIC 整体断电，此时 ramoops 完全无效，只能依赖 Flash 黑匣子。
```dts
reserved-memory {
    #address-cells = <2>;
    #size-cells = <2>;
    ranges;

    ramoops@fff00000 {
        compatible = "ramoops";
        reg = <0x0 0xfff00000 0x0 0x100000>; /* 1MB 保留内存 */
        record-size     = <0x20000>; /* 128KB 内核日志 */
        console-size    = <0x20000>; /* 128KB 控制台日志 */
        pmsg-size       = <0x40000>; /* 256KB 用户态消息 */
    };
};
```

#### (2) 内核 Panic 与用户态段错误双通道转储
1. **内核崩溃自动转储**：内核在死机瞬间，由 `ramoops` 驱动将崩溃前的 `dmesg` 环形缓冲直接拷入这 1MB 内存中；
2. **用户态主应用崩溃捕获（PMSG）**：
   `octopus_app` 注册 `SIGSEGV`、`SIGBUS`、`SIGABRT` 信号处理函数。当发生非法内存越界时，信号函数抓取当前调用栈，直接写入 `/dev/pmsg0`（内核 PStore 暴露给用户态的写入节点）。
   信号处理函数里能做的事非常有限，必须遵守以下约束，否则崩溃处理本身会二次崩溃或死锁：
   - 用 `sigaltstack()` 预先分配备用栈，否则栈溢出引起的 `SIGSEGV` 无栈可用；
   - `backtrace()` 首次调用会加载 libgcc 并分配内存，必须在初始化时先调用一次“预热”；
   - 只用 `write()` 等异步信号安全函数和预分配缓冲区，禁止 `printf`、`malloc`、加锁；
   - ARM32 需以 `-funwind-tables` 编译，否则回溯只能拿到一层；
   - 转储完成后恢复默认处理并重新 `raise()` 原信号，让进程以原本的信号退出，由 supervisor 根据退出原因决定重启进程还是复位整机。

#### (3) 开机自检与提取导出
系统重新启动后，内核自动将这块内存挂载为 `/sys/fs/pstore/` 文件系统。`octopus_app` 在 `EARLY_INIT` 阶段检查该目录下是否存在上一次崩溃的记录文件：
- 若存在，自动将其拷贝至持久化存储 `/data/log/crash/crash_<序号>_<boot_id>.log`，并清除 pstore 缓存。文件名用单调递增序号而不是日期，因为无 RTC 的设备上电时墙上时间不可信；日期写在文件内容里，标注时间来源（NTP 校准 / 最后已知时间）；
- 在 Web 页面和 octopus_cli 命令中提供 `show system crash-log` 一键查看与打包导出。

## 议题 3：产线数据隔离、设备凭证与安全合规（Security & Provisioning）

商业设备量产时，必须实现“代码与凭证分离，出厂重置与私密数据隔离”。确立以下三项资产保护与安全合规规范：

### 3.1 产线关键数据（Factory Information）的物理存放与隔离规范
- **资产范围分类**：
  1. **硬件基础身份**：以太网 MAC 地址（6字节）、设备唯一序列号 SN（16~32字符）、硬件 PCB 版本号；
  2. **生产标定参数（Calibration Data）**：机器人舵机/电机的物理机械零点偏置、ADC 电池电压校准系数、RF 射频发射功率校准参数；
  3. **云端安全身份**：接入 AWS IoT / 阿里云所必需的设备私钥（`device.key`）与 X.509 客户端证书（`device.crt`）。
- **已敲定存储方案：Flash 独立 `factory` 只读分区为主 + 预留 I2C EEPROM 驱动抽象**：
  - **默认存储介质**：在 Flash（eMMC 或 SPI NAND）划分独立的 `factory` 分区（128KB~1MB），正常运行期挂载为只读；在执行 `factory-reset`（出厂重置）时，系统底层**绝对禁止擦除或格式化此分区**；
  - **完整性与冗余**：FACTORY 只有一份时，一次意外擦写或位翻转就会丢失 MAC 与 SN，设备无法再被识别。数据以“版本 + 长度 + 内容 + CRC32”格式存放两份副本，读取时校验并自动选用完好的那份；
  - **统一驱动抽象（Board HAL）**：通过架构文档 6.2 冻结的 `board_hal.h` 访问（`octopus_board_get_info()`、`octopus_board_get_calibration()`），此处不再另定义接口。底层根据设备树（DTS）自适应：若板载了 I2C EEPROM，则从 EEPROM 物理读取；若未外挂，则从 `/dev/octopus/by-vol/factory` 读取，对上层业务完全无感透明；
  - **私钥不应明文存放**：`device.key` 明文放在 FACTORY 分区，夹下 Flash 芯片就能复制设备身份。有安全元件（SE，如 ATECC608、SE050）或 TEE 的机型，私钥应在其中生成且不可导出；没有的机型至少用 SoC 硬件唯一密钥加密存放，并在威胁模型中写明其防护边界。

---

### 3.2 固件防篡改签名与安全启动规范（Secure Boot）
- **安全威胁防御**：防止第三方私自刷入未授权固件、篡改内核或恶意仿冒山寨硬件。
- **已确立技术落地流**：
  1. **发布阶段（Sign）**：在离线签名机或 HSM 上，用厂商私钥（**ECDSA-P256 或 RSA-2048**）对 OFI 头部签名。头部含每个段的 SHA-256、固件版本、防降级计数与板型标识，签名覆盖整个头部（格式见架构文档 4.4）；
  2. **升级校验（Verify in User Space）**：`firmware_worker` 内置对应公钥。先验签头部，并检查板型与防降级计数；通过后流式写入非活动槽，边写边算每段哈希，全部一致才切换启动槽。**头部验签失败直接拒绝，任一段哈希不符则保持非活动槽为 bad 并报警**。这样无需把整个镜像缓存在内存中；
  3. **Bootloader 校验（Verify in Bootloader）**：U-Boot 的 `cmd_ofi.c` 驱动在从 Flash 加载 Kernel 镜像到 RAM 之后、执行跳转前，调用内置轻量公钥库验签；验签失败则停止引导并切回备用分区。

---

### 3.3 核心算法模型权重资产防盗与硬件绑定
- **知识产权保护需求**：客户花费大量人力与算力训练出来的核心 AI 视觉权重文件（厂商 NPU 工具链导出的模型包，例如常见的 `.rknn` 等格式），必须防止被外部人员通过编程器夹芯片读取 Flash 轻易窃取。模型格式与推理库均由芯片/工具链厂商按其许可单独提供，**不纳入本仓库源码树，本项目也不分发其源码或二进制**。
- **为什么不能直接用 Chip ID 派生密钥**：一种常见做法是“用 SoC Chip ID 通过派生算法得到密钥，AES-GCM 加密 `model.squashfs`”。但 Chip ID 可以被软件读出，派生算法就在 Loader 里，攻击者拿到 Flash 镜像和任意一台设备的 Chip ID，就能算出密钥，这属于“靠隐藏算法保密”。而且打包阶段每台设备的 Chip ID 各不相同，无法用同一个镜像批量出货。
- **已确立落地策略：硬件密钥封装 + 块设备加密**：
  1. 打包阶段，用随机生成的模型密钥 K 对模型镜像加密。采用 dm-crypt 支持的 `aes-xts-plain64` 格式，而不是整体 AES-GCM，以便按块随机读取、直接挂载；
  2. 产线阶段，由设备内部**软件读不到**的硬件唯一密钥（SoC 安全存储 / OTP 中的 HUK，经 OP-TEE 或硬件加解密引擎使用）把 K 封装成“设备专属密文”，写入 FACTORY；
  3. 开机阶段，由 TEE 或加解密引擎解封得到 K，通过 dm-crypt 映射后挂载，K 不落盘、不出现在 Flash 上；
  4. **防护边界要写清楚**：这样可以防止“拆 Flash 拷镜像”到其他设备运行。但设备运行时拥有 root 权限的攻击者仍可以从内存中读取解密后的模型，要防这一层，需要在 TEE 内推理或者由 NPU 驱动支持加密模型，这取决于具体 SoC 能力。没有 HUK / TEE 的 SoC 无法提供此项保护，应如实标注。

## 议题 4：第三方依赖供给模式与跨芯片 libc 兼容边界（Dependencies & Sysroot）

`octopus-core` 仓库是一个独立的现代 CMake 代码库，但它运行在一个由底层交叉工具链和库构成的 Linux 世界中。针对第三方库来源与 C 运行时库的兼容性，确立以下两项核心落地规范：

### 4.1 第三方开源库供给模式：分层混合供给模式（已敲定采用模式 B）

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 【模式 B：分层混合供给模式 (极简核心内置 + 重量级外部链接)】           │
 │                                                                        │
 │  1. 轻量小型纯 C/C++ 核心库 (内聚在 octopus-core/3rdparty/):            │
 │     - 例如: cJSON 解析库、轻量 MQTT 嵌入式客户端、微型 Base64/SHA 库    │
 │     - 做法: 随 octopus-core 源码一同使用 CMake 统一编译                │
 │     - 优势: 无论在 x86 PC、WSL2、Docker、SSD20X 还是 RK3568 上，       │
 │             核心基础库与单测套件均可【零环境依赖一键极速编译】！       │
 │                                                                        │
 │  2. 重量级系统服务与网络组件 (由各芯片 BSP 的 Buildroot/Sysroot 提供): │
 │     - 例如: Hiawatha Web 服务器、Dropbear SSH、OpenSSL 密码套件        │
 │     - 做法: 由统一的用户态构建层（Buildroot external tree 等）交叉编译 │
 │             并打包进 rootfs.squashfs，octopus-core 构建时仅通过        │
 │             CMake find_package 链接头文件与库                          │
 │     - 优势: 避免在底座仓库中重复构建大型复杂软件，构建速度快、架构轻盈 │
 └────────────────────────────────────────────────────────────────────────┘
```

- **安全组件不能交给厂商 BSP**：OpenSSL、Dropbear、Web 服务器这类组件经常需要紧急修补 CVE。如果它们随厂商 BSP 提供，每颗 SoC 上的版本都不同、升级节奏受制于厂商，一个漏洞要分别追三家原厂，这正是 1.1 节“SoC SDK 强绑定”问题的翻版。厂商 BSP 通常交付内核、U-Boot，以及**仅以二进制形式提供的启动固件与加速库**（如 NPU 用户态运行时）；此类二进制由设备方按厂商许可自行获取与集成，**不得进入本开源仓库**。其余用户态组件由 Octopus 统一的构建层维护，所有 SoC 使用同一版本；
- **SBOM 与漏洞跟踪**：统一构建层为每个发布版本产出 SBOM（SPDX 或 CycloneDX），用于 CVE 比对和欧盟 CRA 合规。

---

### 4.2 跨芯片 C 运行时库（libc）兼容性编写准则

- **跨芯片工具链差异现实**：
  - **星宸 SSD20X**：属于较早期的 32 位 ARM 平台，工具链基于较保守的 **glibc 2.24** 甚至 **uClibc-ng**；
  - **瑞芯微 RK3568**：现代 64 位 ARM64 平台，工具链普遍采用 **glibc 2.31** 或 **glibc 2.35**。
- **已固化的三项代码编写与编译准则**：
  1. **严禁使用新版 glibc 私有扩展函数**：  
     例如 `getentropy()`（glibc 2.25 引入）、`copy_file_range()`、某些 C11 线程扩展，在老版本工具链上会报链接期未定义符号。底座统一使用最坚固的标准 **POSIX.1-2008 / C99 接口**（如读取 `/dev/urandom` 获取真随机数、标准 `read`/`write` 进行数据拷贝）；
  2. **严禁依赖特定 libc 的内部数据结构大小**：  
     所有跨模块、跨进程通信数据均采用明确固定宽度的强类型（如 `uint8_t`、`uint32_t`、`int64_t`），严禁使用不确定长度的 `long` 或编译器私有位域；
  3. **CMake 强制注入 64 位文件偏移与时间戳宏**：  
     在顶层 `CMakeLists.txt` 中对所有构建目标全局注入编译宏：
     ```cmake
     add_compile_definitions(_FILE_OFFSET_BITS=64 _TIME_BITS=64)
     ```
     `_FILE_OFFSET_BITS=64` 在所有目标工具链上都有效，32 位 SSD20X 也能处理大于 2GB 的文件。
     **`_TIME_BITS=64` 则有前提**：需要 glibc ≥ 2.34，且内核 ≥ 5.1 提供 64 位 time 系统调用。SSD20X 常见的 glibc 2.24 / uClibc-ng + 4.9 内核组合下，这个宏不起作用，`time_t` 仍是 32 位，2038 问题在这类平台上**无法彻底消除**。可行的缓解措施：
     - 自有的文件格式、IPC 协议、日志时间戳一律用 `int64_t`（秒或微秒），不直接序列化 `time_t`；
     - 计算时间间隔一律用 `CLOCK_MONOTONIC`，不受墙上时间回绕影响；
     - 在 CMake 中检测 `sizeof(time_t)`，32 位时在构建日志中给出明确警告，并在产品文档中写明支持期限。

## 议题 5：数据面通用高性能共享内存通道与双平面协同（liboctopus_shm）

当前管理面和事件上报已确定走 Unix Domain Socket (`/var/run/json_ipc.socket`) + JSON-RPC。这对于 95% 的管理面场景（Web 配置、状态巡查、告警推送，频率 < 30Hz）堪称完美。

然而，**通用基础设施绝不能向单一业务场景（如机器人舵机）特化**。在工业控制、高频遥测与智能边缘领域，存在大量要求**微秒级延迟、零拷贝、纳秒级无锁通信**的高吞吐场景。因此，Octopus 确立**“控制面与数据面物理分离”**的通用双平面架构。

### 5.1 共享内存数据通道解决的 4 大通用业务需求
1. **工业高频测控与电力波形录波（DAQ & Power Grid）**：  
   高精度 ADC 电流电压采样（如电力微机保护器要求每秒采样 12.8kHz 做 FFT 分析）、机械振动监测（每秒数万采样点），走 Socket 字符串解析会导致 CPU 瞬间 100% 跑满崩溃，必须走共享内存零拷贝流转；
2. **工业实时现场总线与 PLC 过程映像区（Process Data Image / Fieldbus）**：  
   通过 RS485 / CAN / EtherCAT 轮询外挂传感器与 PLC，要求每 1ms~5ms 所有应用共享一份最新的所有 I/O 寄存器快照；
3. **AI 视觉高密特征向量、激光点云与原始双工音频（Feature / PointCloud / Audio）**：  
   人脸/目标识别输出的 512 维浮点向量、激光雷达每秒数十万空间点云、16kHz 16bit 双工原始音频 PCM 帧，属于持续流动的高吞吐二进制流；
4. **机器人高频硬实时运动控制（Robot Motion Control）**：  
   机器人关节舵机/无刷电机要求 200Hz ~ 1000Hz（1ms~5ms 闭环）的角度与力矩刷新，作为通用数据通道下挂的一个典型 Channel。
   **注意：共享内存只解决“传得快”，不解决“按时到”。** 标准 Linux 内核下，普通线程的调度延迟在负载高时可达数毫秒甚至更久，1ms 闭环需要 PREEMPT_RT 内核、`SCHED_FIFO` 线程、`mlockall()` 与 CPU 隔离，或者干脆把闭环放到 MCU 上，Linux 只下发目标值。见架构文档第 13 章“实时控制的归属”。

---

### 5.2 统一数据通道设计：`liboctopus_shm`

为包容上述所有场景，底座规划通用公共库 **`liboctopus_shm`**。其核心哲学是：**“一套通用的多路复用信元框架，载荷格式完全由业务自定义”**。

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                      应用层 (多种通用业务并存)                         │
 │                                                                        │
 │  [业务 A: 电力高频采样]  [业务 B: 工业总线 I/O]  [业务 C: 机器人电机]   │
 └─────────────┬───────────────────┬───────────────────┬──────────────────┘
               │                   │                   │
               ▼                   ▼                   ▼
 ┌────────────────────────────────────────────────────────────────────────┐
 │        统一通用数据通道层: liboctopus_shm (/dev/shm/octopus_channels)  │
 │                                                                        │
 │  ┌──────────────────────────────────────────────────────────────────┐  │
 │  │ 通用信元头部 (Generic Cell Header - 严格 32 字节对齐):           │  │
 │  │  - channel_id: 通道编号 (0~255，支持动态通道扩展)                │  │
 │  │  - payload_type: 载荷类型 (RAW_WAVEFORM / BUS_IO / MOTION...)    │  │
 │  │  - sequence_id: 64位防跳帧单调递增序号                           │  │
 │  │  - timestamp_us: 微秒级高精度系统时钟戳                         │  │
 │  │  - payload_len: 实际载荷字节长度                                │  │
 │  │  - flags: 保留扩展位 (如是否丢帧告警、关键帧标记)                │  │
 │  ├──────────────────────────────────────────────────────────────────┤  │
 │  │ 业务自描述载荷区 (Payload Data Buffer):                          │  │
 │  │  - 可以是: 工业电能波形采样点 (float waveform[1024])            │  │
 │  │  - 可以是: 工业现场总线 I/O 状态映射表 (uint8_t io_image[512])   │  │
 │  │  - 可以是: 激光点云坐标数组 / 原始音频 PCM 帧                    │  │
 │  │  - 可以是: 机器人关节角度力矩 (仅作为 Channel_ID = 1 的一种载荷) │  │
 │  └──────────────────────────────────────────────────────────────────┘  │
 │                                                                        │
 │  底层并发机制: 基于 C11 原子变量 (stdatomic) 的单生产者-多消费者无锁环形队列│
 └────────────────────────────────────────────────────────────────────────┘
```

- **信元结构定义（C11，自然对齐）**：
  ```c
  /* include/octopus/shm_channel.h */
  typedef struct {
      uint16_t channel_id;    /* 通道 ID: 0~255 */
      uint16_t payload_type;  /* 业务类型: 0x01-采样, 0x02-总线, 0x03-电机... */
      uint32_t payload_len;   /* 载荷长度 */
      uint64_t sequence_id;   /* 帧流水号 (防丢帧检测) */
      uint64_t timestamp_us;  /* CLOCK_MONOTONIC 微秒时间戳 (延迟与抖动分析) */
      uint32_t flags;         /* 标志位 */
      uint32_t reserved;      /* 填充至 32 字节 */
      uint8_t  payload[];     /* C99 柔性数组成员 */
  } octopus_shm_cell_t;

  _Static_assert(sizeof(octopus_shm_cell_t) == 32, "cell header must stay 32 bytes");
  ```
  字段已按自然对齐排列，不需要也不应该加 `__attribute__((packed))`：packed 会让编译器假设结构体可能未对齐，在 ARM 上生成逐字节访问，64 位字段也就无法原子读写。`payload[0]` 是 GNU 扩展，C99 标准写法是 `payload[]`。32 位与 64 位进程共享同一段内存时，这个布局在两边一致（ARM EABI 下 `uint64_t` 均为 8 字节对齐）。
- **核心性能收益**：
  基于 `/dev/shm` 内存映射与原子序号推进，**零内存拷贝，单次传递的 CPU 开销在微秒级以内**。实际端到端延迟取决于消费者被唤醒的方式：忙轮询最低但占满一个核；推荐生产者通过 `eventfd`（经 UDS 传递 fd）或 futex 唤醒消费者，延迟由调度决定。
- **可靠性约束**：
  - **序号锁（seqlock）读法**：消费者读取前后各读一次序号，不一致就丢弃重读；落后超过一圈（被覆盖）时通过 `sequence_id` 跳变发现丢帧，而不是读到半新半旧的数据；
  - **进程崩溃**：共享内存不使用进程间互斥锁，避免持锁进程崩溃后其他进程永久阻塞。生产者重启后先递增“代数（generation）”字段，消费者发现代数变化即重新同步；
  - **权限**：每个通道一个 `/dev/shm` 对象，按“生产者可写、消费者只读”分别设置文件权限，消费者以 `PROT_READ` 映射。

### 5.3 双平面协同矩阵（Control Plane vs Data Plane）

| 协同维度 | 控制面 (Control Plane) | 数据面 (Data Plane) |
| :--- | :--- | :--- |
| **底层通道** | Unix Domain Socket (`/var/run/json_ipc.socket`) | POSIX 共享内存 (`/dev/shm/octopus_channels`) |
| **公共库** | `liboctopus_json` / `liboctopus_client` | `liboctopus_shm` |
| **传输协议** | 文本化标准 **JSON-RPC** | 二进制 **POD 信元头 + 业务定长/环形无锁缓冲** |
| **交互频率** | 低频 (< 30Hz) 或事件驱动（按需触发） | 高频 (100Hz ~ 10000Hz 持续流式) |
| **核心职责** | 负责设备配置、参数下发、状态查询、存盘与运维 | 负责硬实时运动控制、工业波形采集、总线 I/O 快照 |
| **典型接口** | `system.status.get`、`network.ip.set` | `shm_channel_publish()`、`shm_channel_subscribe()` |

## 议题 6：Flash 存储介质物理边界与 Bootloader 升级防变砖（Storage & Bootloader Resilience）

A/B 双分区机制天然保护了内核与应用根文件系统，但针对底层物理介质（NAND 坏块）与 Bootloader 自身单点薄弱环节，必须确立不可逾越的工程防线。

### 6.1 SPI NAND Flash 的物理坏块容错与对齐机制（Bad Block Skipping）

#### (1) 硬件物理特性与差异
- **eMMC / UFS（如 RK3568）**：内部自带硬件 FTL（Flash Translation Layer）控制器，物理坏块管理、磨损均衡与 ECC 纠错对操作系统完全透明，驱动直接以标准块设备（`/dev/mmcblk0`）访问，极少出现坏块穿透；
- **SPI NAND Flash（如 SSD20X 或低成本网关）**：属于裸 Flash，原厂出厂即允许存在 1%~2% 的出厂物理坏块，且在整个使用寿命的擦写过程中会不断产生新的运行期坏块。

#### (2) 底座与工具链落地的三项硬性规则
1. **严禁使用 `dd` 直接写 MTD 分区**：
   `dd` 将目标设备视为物理连续空间，完全缺乏感知 MTD 坏块的能力。一旦刷写写入到坏块扇区，内核会抛出 I/O 错误并直接中断写入，导致固件损坏。
2. **固件槽位放在 UBI 卷中，由 UBI 负责坏块**：
   SLOT_A / SLOT_B 是同一 UBI 设备中的静态卷。`firmware_worker` 通过 `UBI_IOCVOLUP` 整卷更新写入，U-Boot 通过 `ubi read` 读取。坏块替换、磨损均衡、位翻转后的数据搬移（scrub）都由 UBI 在两端以相同方式处理。
   这比“裸 MTD + 手工跳坏块”可靠得多，因为后者有两个处理不了的问题：
   - 运行期在槽位中间新增一个坏块，后面的数据整体后移，分区尾部余量不够时镜像就放不下；
   - 固件长期只读，NAND 会因读干扰和数据保持期衰减逐渐积累位翻转，需要有人把数据搬到新块上。UBI 在读到可纠正的位翻转时会自动搬移；裸 MTD 下没人做这件事，几年后同一块数据就会超出 ECC 纠错能力。
3. **裸 MTD 区域才需要手工跳坏块，且两端必须对称**：
   BOOT / ENV / FACTORY 仍在裸 MTD 上，由产线工具或救援工具写入：
   - 遍历目标 Flash Block，调用 `ioctl(fd, MEMGETBADBLOCK)` 检测当前块是否为坏块；
   - **遇到坏块自动跳过（Skip Bad Block）**，顺延写入下一个健康物理块，分区末尾预留余量；
   - 写入后回读校验。`ECCGETSTATS` 显示可纠正位翻转增多时，正确的做法是把该块内容重新写到新块（scrub），而不是直接标记为坏块；只有擦写失败才标记坏块。
   U-Boot 读取这些区域时使用相同的跳块语义：raw NAND 用 `nand_read_skip_bad()`，SPI-NAND 走 MTD 子系统的 `mtd read`（自动跳过坏块）。

### 6.2 Bootloader（U-Boot）升级策略：是否允许 OTA？

在绝大多数嵌入式硬件设计中，物理 Flash 的最前端（Sector 0 开始）只存放了一份 SPL / U-Boot。**这通常是一个没有 A/B 备份的单点薄弱环节**。如果在刷写 Bootloader 的微秒瞬间突发掉电，设备将彻底变砖，现场只能返厂动用治具或烧录夹。

#### (1) 三种工程策略与权衡矩阵

| 策略模式 | 具体做法 | 变砖风险 | 适用场景与决策依据 |
| :--- | :--- | :--- | :--- |
| **策略 A：绝对禁止 OTA 升级 Bootloader (默认强制要求，强烈推荐)** | OFI 固件升级包内**严禁包含 U-Boot 二进制**。U-Boot 在出厂产线一次性烧录固化，后续升级永远只针对 Kernel 与根文件系统（A/B 双分区）。 | **不会因 OTA 写 Bootloader 而变砖**（只要 Bootloader 不死，设备总能通过 A/B 自动仲裁或网络救援恢复）。代价是 U-Boot 的漏洞与签名密钥永远无法远程更新，所以 U-Boot 出厂前必须内置备用公钥与吊销机制。 | 工业交换机、高可用网关、野外无人值守设备的通用最佳实践。**Octopus 默认固件规范严格执行此策略。** |
| **策略 B：受限的工程救援模式 (Local Recovery Only)** | 正常 OTA 固件包严禁携带 Bootloader。仅在硬件底层存在严重 DDR 时序 Bug 时，提供独立的专用工具，要求在外部稳定供电、人工二次输入确认命令的限制下单独刷写，写完立即执行全量回读校验。 | **中等风险**（刷写微秒级瞬间若强行拔电则变砖）。 | 仅限售后技术人员返修、产线重工或特种实验室环境。 |
| **策略 C：硬件支持的 Bootloader 双备份 (需芯片物理支持)** | 依赖芯片 BootROM 的多副本加载机制（例如在约定偏移处搜索多份 SPL，或从 eMMC boot0 / boot1 硬件分区轮询启动）。各 SoC 支持情况差异很大，必须以芯片手册和实测为准。在物理层真正实现 U-Boot 的 A/B 热备。 | **极低**（但强依赖特定 SoC 的 BootROM 硬件引脚配置或 eFuse 熔丝定义）。 | 高预算定制硬件方案。 |

#### (2) Octopus 底座的明确决策
**将“策略 A（禁止 OTA 升级 Bootloader）”固化为系统默认的顶级安全准则**：
1. `ofi_pack` 打包脚本默认拒绝将 Bootloader 编入通用 `.ofi` 固件中；
2. `firmware` 用户态升级服务在校验 OFI 头部 TLV 时，若发现包含 Bootloader Chunk，默认直接拒绝刷入并返回非法类型错误；
3. 确保任何远程升级、Web 页面升级或批量推送升级，无论在哪一步掉电，都不会让设备失去可引导的槽位。

### 7.1 核心诊断与自省机制深度剖析

#### (1) `lock_watchdog`：临界区互斥死锁监测与持锁性能分析器 （`lock_watchdog` 模块）
高可靠架构中的 `lock_watchdog` 远不止是一个普通的 `pthread_mutex` 封装，而是一个功能完整的**锁状态看护与竞争诊断子系统**：
*   **内存防踩踏魔数（Canary）**：`lock_watchdog_t` 结构体头部设置了 `cookie = 0x0BADBABE`。每次加锁/解锁前强制校验该魔数，一旦互斥锁结构体被外部野指针或缓冲区越界破坏，立即报错拦截；
*   **加锁历史追踪（Flight Recorder）**：结构体内置深度为 16 的环形数组 `lock_attempt_thread_id[16]`，记录最近 16 次加锁尝试的线程 TID、文件名、代码行号及 pending 状态；
*   **后台巡检与死锁超时判定**：独立后台线程 `lock_watchdog_thread` 每 5 秒遍历全局注册链表中的每一把互斥锁。若某把锁持续被同一线程持有超过门限（默认 `max_lock_time = 10s`，与架构文档 9.2 的统一时间线一致；门限必须小于硬件看门狗超时，否则还没判定死锁整机就已被复位，现场什么也留不下），立即判定为**死锁**；
*   **持锁性能瓶颈剖析（Profiling）**：统计记录每把锁的历史**最大持锁时长**（`max_lock_tick_cnt`）以及发生此最大耗时的源码位置（`max_lock_file`、`max_lock_line`），帮开发人员在线精确定位多线程锁竞争瓶颈；
*   **防呆防御断言**：提供 `lock_watchdog_assert_locked()`。在所有假设“调用者已持有锁”的内部函数入口加入断言，在多线程业务重构时彻底杜绝并发竞态漏锁。

#### (2) `crashhandler`：全系统多线程协同崩溃快照系统 （`crashhandler` 模块）
在多线程 Linux 程序中，单个线程触发段错误（`SIGSEGV`）时默认生成 core dump 或直接闪退，无法获知**其他存活兄弟线程在崩溃瞬间正在做什么**。系统设计了高度协同的现场转储协议：
*   **首死线程领导权**：捕获异常信号的线程被标记为 `first_thread_to_die`，负责记录自身寄存器（PC、SP、通用寄存器）及调用栈；
*   **全线程唤醒广播**：首死线程打开 `/proc/self/task/` 目录枚举进程下所有兄弟线程的 TID，通过系统调用 `syscall(SYS_tgkill, pid, tid, SIGRTMIN + 1)` 给全系统所有兄弟线程发送专用的转储信号；
*   **多线程协同并发转储**：全系统每个存活工作线程各自在自身上下文中打印线程名、TID，并执行 `_Unwind_Backtrace()` 打印出崩溃瞬间自己的调用栈，拼装成整机**全景调用栈快照**；
*   **黑匣子持久化与受控退出**：首死线程等待所有兄弟线程转储完成（最多等待 3 秒，必须远小于看门狗超时），追加 `/proc/self/maps`、build-id 等关键信息写入 pstore，再尽力写入 `/data/log/crash/`，随后以原信号退出进程。**是否复位整机由 supervisor 决定**：偶发崩溃只重启进程，连续崩溃超过阈值才交给看门狗复位。崩溃处理函数自己调用 `reboot()`，会让 supervisor 的退避重启策略失去意义，也会把一次可以局部恢复的进程崩溃放大成整机重启。

#### (3) `octopus_alloc`：模块化堆内存安全金丝雀与泄漏追踪 （`octopus_alloc` 模块）
针对嵌入式长期运行环境中的内存泄漏和缓冲区溢出踩踏（Heap Corruption）：
*   **双魔数金丝雀（Canary & Redzone）**：
    *   分配时头部多申请 8 字节：前 3 字节设为魔数 `0xC0FFEE`，高 1 字节记录 `modid`（模块 ID），后 4 字节记录用户申请尺寸 `sz`；
    *   尾部附加 1 字节：设为尾部魔数 `0xBA`；
    *   释放时严格校验前后的魔数。若魔数被改写，立即打印越界踩踏发生时的指针地址、被踩踏模块名及源码行号；
*   **模块级堆内存统计与泄漏秒级定位**：
    *   为全系统每个模块维护独立的计数器：当前内存用量（`usage`）、历史峰值（`max`）、分配次数（`allocs`）、释放次数（`frees`）；
    *   通过 CLI 输入 `show memory`，若发现某个模块的 `allocs` 远远大于 `frees`，且 `usage` 持续单调递增，**无需挂接调试器即可在线确认是哪一个模块发生了内存泄漏**。

#### (4) `thread_load_monitor`：线程级 CPU 负载与调度颠簸监视 （`thread_load_monitor` 模块）
全系统 CPU 负载高不可怕，可怕的是不知道是哪个具体线程在狂转：
*   **单线程高精负载计算**：周期性采集 `/proc/stat` 与 `/proc/self/task/<tid>/stat`，计算全系统 Idle 负载、中断/外围进程负载，以及**系统中每一个工作线程**的 1 秒瞬时负载与 10 秒滑动平均负载（多线程嵌入式专用 `htop`）；
*   **上下文切换与调度瓶颈**：统计每个线程的上下文切换次数（自愿 vs 被迫 Context Switch），若某个线程频繁出让 CPU，可直接发现锁竞争剧烈或休眠粒度不合理；
*   **缺页中断监控（Page Faults）**：解析 `/proc/vmstat` 中的 `pgfault` 变化率，在内存紧张出现页面抖动或 swap 颠簸时发出预警。

#### (5) `octopus_trace`：三维动态日志追踪系统 （`octopus_trace` 模块）
*   **三维细粒度过滤**：每一条 Trace 语句都由 **[模块 ID, 组 Group ID, 线程 TID]** 三维标识，并拥有独立等级（`ERROR` -> `RACKET` 共 6 级）；
*   **编译期零开销裁剪**：通过 `octopus_trace_LVL_MIN` 可以在 Release 版本中将调试级宏完全展开为空，零指令、零字符串体积占用；
*   **运行期热拔插调节**：生产环境中默认全部为 `ERROR` 级别（零损耗）；一旦现场某个功能（如 LACP、电机驱动、MQTT）出现偶发异常，现场工程师只需通过命令行敲入一条指令，即可将该单一模块动态开启为 `DEBUG` 或 `NOISE`，无需重启进程，日志抓取完毕后随手关闭。

#### (6) 业务性能与队列水位监视 (`packet_dbg` 与 `msg_dbg`)
在通信与报文转发层面，系统加入了对**恶性慢回调**的捕获：
*   **慢回调抓包（`longest_rx_callback_ticks`）**：分发线程向业务模块回调分发数据前后打时间戳，统计每个业务模块注册的回调函数消耗的最大时间，防止业务模块在回调中执行磁盘写操作或休眠阻塞整条流水线；
*   **缓冲区水位与未释放统计（Outstanding Buffers）**：全局统计 `Allocations`、`Deallocations` 与当前漂浮在系统中的 `Outstanding` 数量，防止报文池泄漏；
*   **FIFO Over / Under 统计**：统计硬件 FIFO 与软件环形队列溢出次数。

#### (7) `post`：开机硬件自检与外设枚举 （`post` 模块）
开机时对硬件各个总线与器件执行自检（BIST、DDR 压力校验、EEPROM 读写回环、I2C 总线挂载扫描、网口物理回环测试），结果存入 `post_status_table`，系统启动后形成开机硬件健康体检报告。

#### (8) `syslog_flash`：掉电不丢失的硬件黑匣子 （`syslog_flash` 模块）
普通系统的日志全在 RAM 或 Linux 日志缓存中，一旦系统遭遇掉电、看门狗硬复位或 Kernel Panic，最后发生崩溃的现场日志全部灰飞烟灭。高可靠系统划分了独立的 Flash 环形日志区（`syslog_flash_log`），将最致命的致命错误（`OCTOPUS_ASSERT`、死锁告警、致命异常）直接原子刷写到 Flash，重启后可调取死前遗言。

| **`post` 硬件自检** | `liboctopus_board` | 1. 抽象为通用硬件自检插件机制：RK3568/SSD20X 上电后依次自检 I2C 外设（RTC/EEPROM）、PHY 芯片、共享内存环回通道 | **P2 (推荐)** |
| **慢回调抓包监视** | `liboctopus_shm` / `bus` | 在 Octopus 的 RPC / SHM 数据处理流水线中，记录每次处理回调的最大耗时，防业务阻塞线程 | **P1 (强烈推荐)** |

### 7.3 关键工程争议、方案推演与决策过程记录

#### (1) 决策 1：`lock_watchdog` 锁监护的默认使能策略
*   **争议选项**：
    *   **方案 A**：**全生命周期默认开启**（微秒级开销可忽略不计，换取全天候死锁检测与持锁性能监护）；
    *   **方案 B**：仅在 Debug / CI 测试固件中开启，Release 固件中宏退化为原生 `pthread_mutex`。
*   **方案推演与决策依据**：
    *   **决定采用方案 A（全生命周期默认开启）**；
    *   **核心依据**：高可靠工业系统即使在商业出货版本中也默认开启锁监护。嵌入式现场很多偶发性死锁需要运行数周甚至数月才会在特定时序下复现一次。如果量产版本关闭，一旦设备在客户现场卡死，外部看门狗复位后根本无法留下任何证据，永远无法定位死锁点；
    *   **与议题 2（系统容灾）深度联动**：后台巡检线程发现任何锁持锁超过 10 秒，立即判定为死锁，第一步调用 `lock_watchdog_dump` 将全系统锁持有关系与调用栈输出至黑匣子日志，第二步**主动停止喂看门狗**，交由硬件看门狗在 20 秒超时后彻底硬件复位。

---

#### (2) 决策 2：`octopus_alloc` 内存金丝雀与模块用量统计的方案推演与推荐

针对内存监控的开销与量产策略，团队展开了深度工程推演：

##### ① 为什么不推荐量产版完全关闭（方案 A 的缺陷）
如果在量产版本中把 `octopus_alloc` 彻底关闭、直通 glibc 的 `malloc/free`：
*   **现场事故盲盒**：嵌入式设备在客户现场最致命的故障之一是**慢速微量内存泄漏**（例如某模块每小时漏 10KB，运行 3 个月后触发 OOM 崩溃）；
*   一旦发生 OOM，你只能看到整个进程占用了 500MB，但**没有任何手段知道是哪一个模块漏了内存**；
*   在现场无法挂 GDB、无法跑 Valgrind（内存和算力支撑不起）的情况下，团队将被迫在成千上万行代码中盲猜排查，修复周期长达数周。

##### ② 为什么 7.1(3) 描述的传统实现在现代多核下不能直接用（方案 B 的陷阱）
7.1(3) 的传统实现在现代 SoC（如 RK3568 四核 Cortex-A55、SSD20X 双核）上存在两个硬伤：
1.  **全局互斥锁瓶颈**：每次 `alloc` / `free` 都要抢一把全局互斥锁 `alloc_crit`。单核时代影响较小，但在 4 核 ARM64 并发处理多线程网络报文、JSON-RPC 解析时，这把全局锁会导致严重的 CPU 上下文切换与锁竞争；
2.  **指针对齐风险**：头部附加 8 字节。ARM64 上 glibc 的 `malloc` 保证返回 **16 字节对齐**的指针（满足 NEON 与 `long double` 等类型的要求），头部只有 8 字节时，交给调用方的指针只剩 8 字节对齐，存放 16 字节对齐类型的对象就会出错或降速。尾部单字节魔数本身不影响返回指针，但会让实际块尺寸落在奇数边界上。

##### ③ 终极敲定：方案 C ——「分级双轨制」（现代工程最佳实践）

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   Octopus 模块化内存健康体系 (双轨制)                   │
├───────────────────────────────────┬────────────────────────────────────┤
│ 轨 1：量产版 / 现场常驻 (Production)│ 轨 2：研发 / CI / 自动化测试 (Debug) │
├───────────────────────────────────┼────────────────────────────────────┤
│ • 无锁原子计数 (C11 stdatomic)    │ • 前后 Redzone 内存金丝雀 (Canary) │
│ • 16 字节严格对齐头部             │ • 越界踩踏精准捕获与行号追溯       │
│ • 秒级定位“哪个模块在漏内存”      │ • 配合 GCC AddressSanitizer (ASan) │
│ • 性能损耗 < 1%，纳秒级开销       │ • 严格拦截 Use-After-Free          │
└───────────────────────────────────┴────────────────────────────────────┘
```

*   **生产轨（Release 固件默认全天候使能）—— 彻底解决“谁在漏内存”**：
    *   **无锁原子计数（Zero-Lock）**：使用 C11 `atomic_uint_least64_t` 计数（32 位计数器在高频分配的模块上几天就会回绕），去掉 `alloc_crit` 互斥锁，多核并发分配零阻塞；
    *   **标准 16 字节 Header**：在内存块头部填充对齐的元数据（包含 `uint32_t module_id` 和 `uint32_t size`，填充至 16 字节），保证返回给上层的指针绝对符合 ARM64 内存对齐要求；
    *   **模块归属与覆盖范围**：C++ 代码通过重载全局 `operator new/delete` 接入，模块 ID 取自线程局部的“当前模块”标记（模块回调入口处设置）。第三方库内部直接调用 `malloc` 的内存不经过 `octopus_alloc`，报表中单列为 `UNTRACKED`（用进程总堆用量减去已跟踪量得到），避免让人误以为报表覆盖了全部内存；
    *   **在线现场自省**：任何时候现场出问题，无论是通过 CLI 还是 JSON-RPC 调取诊断接口，都能瞬间拉出各个模块的内存健康报表：
        ```text
        octopus# show memory modules
        Module             Allocs       Frees      In-Use (B)    Peak (B)   Status
        ------------------ ----------- ----------- ----------- ----------- --------
        SYS_MAIN                  1240        1240           0      131072   OK
        NET_LACP                 85200       85200           0       16384   OK
        RPC_SERVER              128400      128400        2048       65536   OK
        MQTT_CLIENT             450120       12000     8912896     8912896   WARN: LEAKING!
        UNTRACKED                    -           -     1245184     1310720   -
        ```
        **收益**：一眼就能锁定是 `MQTT_CLIENT` 模块的 `Allocs` 远大于 `Frees` 且用量持续上涨，现场排错能力直接拉满，性能损耗几乎测不出来（< 1%）。（AI 视觉是独立进程，不在 `octopus_app` 的报表里，它的内存由 supervisor 按进程统计。）
*   **测试轨（研发、CI 自动化测试、老化房压测开启）—— 彻底解决“谁在踩内存”**：
    *   在固件编译时通过 `-DOCTOPUS_MEM_CANARY=ON` 开启前后魔数金丝雀（Redzone）；
    *   在三层测试金字塔（L1 单元测试、L2 模块级集成测试）中直接开启 GCC/Clang 原生的 `-fsanitize=address` (ASan)。现代 ASan 在上位机仿真与开发板测试时对内存踩踏、野指针、Use-After-Free 的捕获精准度远超手写的简单魔数。

#### (3) 决策 3：崩溃全景转储 (`crashhandler`) 的落盘路径与协同机制
*   **多线程协同快照**：采纳 7.1(2) 中首死线程通过 `/proc/self/task/` 广播信号的机制（广播使用专用实时信号如 `SIGRTMIN+1`，不要用 `SIGABRT`，以免与真正的 abort 混淆），确保段错误发生瞬间，所有存活工作线程（网络、IPC、电机控制等）各自转储当时的调用栈，形成全景多线程快照；
*   **现代堆栈回溯**：采用现代标准 `libunwind` 替代老旧的 `_Unwind_Backtrace`，全面支持 ARM64、ARM32 与 x86_64 寄存器现场打印；
*   **落盘路径双保险策略**：
    1.  **第一优先级（RAMoops / pstore）**：将崩溃快照写入内核保留的 1MB RAMoops 内存区。因为在内存崩溃瞬间，文件系统可能处于锁死或不稳定状态，RAMoops 纯内存写可在纳秒级完成，杜绝落盘 I/O 阻塞；
    2.  **第二优先级（Flash 持久文件）**：尝试写入 `/data/log/crash/`（全仓库统一的崩溃目录，受日志配额约束），并同步打印到串口控制台；
    3.  **受控退出**：转储完成后以原信号退出进程，由 supervisor 按退避策略重启，连续崩溃超过阈值才由看门狗复位整机（见 7.1(2) 与架构文档 5.3）。
